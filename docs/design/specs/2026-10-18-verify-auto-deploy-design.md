# 검증 통과 커밋 자동 배포 설계

- 날짜: 2026-10-18
- 상태: 구현됨. 규칙 정본은 [`docs/features/verify.md`](../../features/verify.md) "배포"와
  [`docs/features/daemon-lifecycle.md`](../../features/daemon-lifecycle.md)로 옮겼다. 이 문서는 결정의 기록이다

## 한 줄

**`verify` 대상에 `deploy: true`를 켠 main 빌드 기기에서는 검증을 통과한 커밋을 데몬이 직접
`rocky update --main <sha>`로 올린다.** 배포를 맡을 세션이 따로 필요 없다. 기능 표의 *받아 온다*(기본 브랜치 검증)와
*바탕*(데몬 수명의 업데이트) 줄에 붙는다.

## 왜

- **지금은 세션이 배포한다.** `rocky verify subscribe`로 구독한 세션이 통과 알림(`session_notice`)을 받고
  `rocky update --main`을 실행한다. 구독은 세션 하나에 묶여 있어서, 그 세션이 끝나면 통과 알림은 "받을 세션 등록 없음"으로
  버려진다.
- **2026-10-17에 네 번째로 끊겼다.** 배포를 맡던 rocky rc 서버의 메인 세션이 #490(rc 서버는 세션 없이 서버만 띄운다)
  뒤로 다시 생기지 않았다. #491-#493의 통과 알림이 버려졌고 Mac은 c05f350(#490)에 머물렀다. 오너 규칙은
  "Mac은 늘 main 최신"(2026-10-03)이다.
- **성공 기준**: 켠 뒤 머지된 커밋이 사람이나 세션 없이 검증 통과 몇 분 안에 Mac에 깔린다(`/api/health`의 `commit`).
  실패는 배너로 한 번 보인다.

## 결정 표

| # | 질문 | 결정 | 버린 것과 이유 |
|---|---|---|---|
| 1 | 누가 배포를 시작하나 | **데몬의 검증 잡.** 통과를 가장 먼저 알고 launchd로 늘 떠 있다 | 세션 구독(지금): 세션 수명에 묶여 네 번 끊겼다. 기기 스크립트를 launchd 타이머로 실행: 판단이 레포 밖에 있어 테스트와 문서가 없고, 검증 결과를 따로 읽어야 한다 |
| 2 | 무엇을 실행하나 | **고정 argv** `<데몬 옆 rocky> update --main <sha>`. `--yes`는 넘기지 않는다 | 설정에 적는 일반 명령(통과 뒤 훅): 쓸 곳이 rocky 하나뿐이고, 데몬을 교체하는 명령에 필요한 분리 실행 규칙을 모든 명령에 강요한다 |
| 3 | 언제 시작하나 | **바퀴마다 맞춘다.** 마지막으로 통과한 커밋과 깔린 main 빌드(`main/.finished`)가 다르면 시작한다. 그 뒤 다음 커밋의 실행이 실패해도 통과한 커밋은 그대로 대상이다 | 통과한 순간에만 시작: 그 사이 데몬이 다시 뜨거나 통과가 겹치면 놓친다 |
| 4 | 언제 켜지나 | **네 조건을 모두 채울 때만.** 사용자 `rocky.json`의 `verify.targets[].deploy: true`, main 빌드 모드(`current` → `main`), 대상 보드의 `repo`가 `main_build::CLONE_URL`의 레포(`minjun0219/rocky`), 대상 `branch`가 `main`. `update --main`은 origin/main 위의 커밋만 받으므로(`resolve_want`) 다른 브랜치의 통과 커밋을 넘기면 매번 실패한다 | 모드 자동 전환: 마켓플레이스를 바꾸면 플러그인에 저장된 옵션과 데이터가 지워진다. 그래서 `update_main`도 전환 전에 확인을 받는다 |
| 5 | 실패하면 | **옛 데몬이 그대로 동작한다**(빌드에 실패하면 교체 전에 멈춘다). 그 커밋은 자동으로 다시 시도하지 않는다. 배너를 한 번 띄우고 `rocky verify`에 남긴다 | 자동 재시도: 빌드가 깨진 기기에서 몇 분짜리 release 빌드를 되풀이한다 |
| 6 | CI 결과도 보나 | **보지 않는다.** 그 기기의 검증 단계가 게이트다. 새 커밋 감지(`git ls-remote`)처럼 GitHub API 예산을 쓰지 않는다 | CI 상태 조회: 모든 세션의 `gh`와 같은 예산을 쓴다 |
| 7 | 세션 구독은 | **남긴다.** 배포가 켜진 대상이면 알림 문구만 "데몬이 이 커밋을 배포한다"로 바꾼다 | 구독 제거: 결과만 기다리는 쓰임이 남아 있다. 문구를 그대로 두면 세션과 데몬이 같은 커밋을 두 번 올린다(잠금 때문에 두 번째는 건너뛰지만 헷갈린다) |

## 흐름

```
검증 잡의 한 바퀴
 └─ deploy_plan(설정, 모드, 마지막 통과, 배포 기록, 깔린 빌드와 조상 여부, 실행 중인 배포)
     ├─ Skip(이유): 이유가 바뀔 때만 데몬 로그에 한 줄
     └─ Start(sha)
         └─ 새 프로세스 그룹으로 <데몬 옆 rocky> update --main <sha>를 실행하고 바로 pid와 함께 deploy.json에 기록
             ├─ 빌드·준비 실패: 옛 데몬이 종료 코드를 받아 failed로 기록하고 배너
             └─ update 안의 daemon restart로 데몬 교체
                 └─ 새 데몬이 바퀴마다 판정: 그 pid가 끝났고 main/.finished가 sha면 succeeded,
                    끝났는데 다르면 failed(플러그인·agy 단계), 아직 실행 중이면 다음 바퀴에 다시 본다
```

## 규칙

- **판정은 순수 함수로 둔다.** `rocky_core::verify`(또는 새 `deploy` 모듈)에 `deploy_plan`을 두고 `rockyd::verify`는
  배선만 한다.
- **스위치는 기동 때 읽는다.** 검증 블록 전체가 그렇다. `deploy`를 바꾸면 `rocky daemon restart`가 필요하다.
- **실행은 rc 서버와 같은 방식으로 분리한다.** `process_group(0)`으로 새 프로세스 그룹을 만들고, `kill_on_drop`은 쓰지
  않는다. `XPC_SERVICE_NAME`을 지우고 stdin은 비운다. 출력은 `<검증 대상 디렉터리>/deploy-<sha12>.log`(0600, 최근 5개)에
  쓴다. launchd는 데몬 잡을 내릴 때 잡의 프로세스 그룹만 정리하므로 새 그룹의 자식은 살아남는다(2026-10-05 rc 실측).
  데몬을 교체하는 update가 그래서 끝까지 실행된다.
- **argv의 sha는 `git ls-remote`에서 받은 40자 16진 문자열만 쓴다.** REST와 화면에는 배포를 시작하는 길이 없고, 설정
  스위치만 있다.
- **`--yes`를 넘기지 않는다.** 마켓플레이스를 바꿔야 하는 기기(아직 main 모드가 아닌 기기)에서는 update가 터미널이 없어
  확인을 받지 못하고 멈춘다. 결과는 failed다. 4번의 모드 조건 위에 겹친 안전장치다.
- **실행 중인 배포는 pid와 그 프로세스의 시작 시각으로 확인한다.** 검증의 `running.pgid`와 같은 방식(`ps -o lstart=`)이라
  재사용된 pid를 실행 중으로 보지 않는다. main 빌드는 기기에 하나라 대상을 가리지 않고 본다.
- **다른 main 빌드가 `main-sync.lock`을 쥐고 있으면 띄우지 않는다.** 세션이나 사람의 `rocky update --main`, 기기의 빌드
  스크립트가 쥔다. 그때 띄우면 update가 잠금에 걸려 그 커밋의 실패로 남는다. pid가 없는 잠금도 쥔 것으로 본다(update와 같다).
- **배포가 실행 중이면 검증 잡은 새 실행을 시작하지 않는다.** 시작해도 데몬이 교체되면서 끊기고 다시 실행된다.
- **앞으로만 간다.** 깔린 빌드가 통과한 커밋의 조상일 때만 시작한다(`git merge-base --is-ancestor`). 검증이 끝나기 전에
  사람이 더 새 커밋을 손으로 올렸으면 옛 통과 커밋으로 되돌리지 않는다.
- **같은 커밋은 자동으로 한 번만 배포한다.** 성공이든 실패든 한 번 띄운 sha는 다시 띄우지 않는다. 사람이 `.finished`를 그보다
  옛 커밋으로 바꿔도 마찬가지다(되돌린 것을 다시 덮지 않는다). 새 커밋이 통과하면 그 커밋이 대상이 된다.
- **기록**: `deploy.json`(sha, pid, 시작·끝 시각, 결과, 로그 경로)과 `runs.jsonl`의 `deployed`·`deploy-failed` 줄.
  `GET /api/verify`와 `rocky verify`는 대상 아래에 배포 한 줄을 보여 준다.
- **알림**: 실패만 배너로 알린다(검증 배너와 같은 notifier). 성공은 알리지 않는다. 세션 알림 문구는 7번을 따른다.
- **사용 로그에는 넣지 않는다.** 배포는 사람이 부르는 표면이 없다. 얼마나 쓰였는지는 `runs.jsonl`의 배포 줄로 센다(새
  `UsageSource`를 만들지 않는다).

## 범위 밖

- 열린 세션에 `/reload-plugins`를 알리는 일. update가 안내를 출력하지만 보는 사람이 없는 것은 지금과 같다. 필요해지면
  훅 주입으로 따로 다룬다.
- rocky가 아닌 레포의 배포, 릴리스 모드 기기의 자동 업데이트.
- 배포 시각 고르기(밤에만 등). 요청이 없다.

## 검증 방법

- `rocky-core`: `deploy_plan` 표 테스트. 꺼짐, main 모드 아님, 레포가 rocky가 아님, 브랜치가 main이 아님, 통과 아님,
  이미 깔림, 깔린 빌드가 더 새 커밋, 배포 실행 중, 실패한 sha, 새 sha.
- `rockyd` 통합 테스트: 가짜 spawn을 `RcOps`처럼 주입한다. 통과하면 argv와 `deploy.json`을 확인하고, 실패로 끝나면 failed와
  배너와 같은 sha 건너뛰기를 확인한다. 새 데몬의 판정(`.finished`가 같음, 다름, 실행 중)과 배포 중 검증 잡 멈춤도 본다.
- 실기기(오너 Mac): 켠 뒤 첫 머지에서 확인한다. launchd PATH에서 git, cargo, bun, claude를 찾는지, `claude plugin install`이
  되는지, rc 서버가 그대로인지. 처음 한 번은 세션 구독도 남겨 두고 지켜본다.
