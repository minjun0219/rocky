# 이중 구조와 싱크 — 설계 (로컬 데몬 + 클라우드 중계소, Linear식 클라이언트)

- 날짜: 2026-10-15
- 결정자: 오너 (방향: 이 문서의 A안, 로컬 싱크부터)
- 상태: 1번 조각은 머지됐다(2026-10-16). 2번 조각 구현 중. 3·4번 조각은 개요만 있고, 시작할 때 이 문서에 더한다

## 한 줄

**데몬은 계속 그 기기 보드의 정본이다.** 동기화를 켠 기기에서는 Cloudflare의 Durable Object 하나가 중계소가 되어,
맥이 잠든 동안 폰에서 한 쓰기를 받아 두었다가 데몬이 연결되면 넘긴다. 웹 화면은 로컬과 클라우드 모두 Linear처럼
기기에 사본을 두고, 쓰기는 먼저 화면에 반영하고, 바뀐 행만 받는다.

## 왜

- **두 가지 쓰임.** 데스크톱 중심 기기는 지금처럼 맥 안에서만 쓴다. 모바일 중심 기기는 맥이 잠들어 있어도 폰에서
  보드를 보고 고치고 싶다. 지금 원격 접근(Cloudflare Tunnel + Access)은 맥이 깨어 있어야 열린다.
- **웹이 느리다.** 데몬 처리 시간은 이미 짧다. 2026-10-01~15 사용 로그에서 웹이 부른 `GET /api/todos`의 처리 시간은
  p50 8ms다. 느린 곳은 웹이 쓰기마다 서버 확정을 기다리고(`web/store.ts`의 "낙관적 갱신을 하지 않는다"), 이름 없는
  변경 알림(SSE)마다 목록을 통째로 다시 받고, 60초마다 전부 다시 받는 구조다. 같은 기간 웹은 `GET /api/logs/worklog`를
  10,180번, `GET /api/handoffs`를 5,879번 불렀다. 폰에서 터널로 들어오면 이 왕복이 모두 인터넷을 건넌다.
- **Linear의 방식.** Linear는 처음 한 번 데이터를 받아 IndexedDB에 두고, 데이터베이스 전체에 하나뿐인 순번
  (`lastSyncId`) 이후의 변경만 WebSocket으로 받는다. 쓰기는 트랜잭션으로 먼저 화면에 반영하고, 서버가 거절하면
  되돌린다. 충돌은 서버에 도착한 순서로 정하고(필드 단위), CRDT는 긴 글(이슈 설명)에만 쓴다. 이슈 번호는 서버가
  매긴다. rocky도 같은 모양으로 간다.

## 결정

1. **데몬이 정본이다.** 웹·TUI·클라우드는 모두 데몬의 클라이언트다. 번호 매기기와 자동화(PR 감시, 핸드오프,
   doing 귀속)는 데몬만 한다.
2. **클라우드는 중계소다.** Cloudflare Worker와 SQLite Durable Object(DO) 하나. DO에는 데몬이 확정한 행의 사본과,
   데몬이 연결되지 않은 동안 받은 쓰기(보낼 변경함)만 둔다. 데몬이 연결되면 변경함을 넘기고, 데몬이 확정한 행으로
   사본을 바꾼다.
3. **연결은 데몬이 먼저 건다.** 데몬이 바깥으로 WebSocket 하나를 연다(Access 서비스 토큰). 맥에 들어오는 문을 새로
   열지 않는다.
4. **기기별 opt-in.** [`docs/rewrite/decisions.md`](../../rewrite/decisions.md) "확장 경로 제약"(2026-08-31)을
   그대로 따른다. 기본은 로컬 전용이고 설정 키는 그때 비워 둔 `todo.sync`다. 데몬 코어는 클라우드를 모르고, 연결기는
   다른 클라이언트와 같은 싱크 프로토콜로 바뀐 행을 받는다. 동기화를 켜지 않은 기기의 보드 데이터는 어떤 경로로도
   기계를 떠나지 않는다.
5. **충돌은 데몬에 도착한 순서로 정한다.** 쓰기는 필드 단위 패치라서 나중에 도착한 패치의 필드가 남는다. 진 값은
   히스토리에 남는다. 노트 본문은 지금의 CRDT(Yjs)를 그대로 쓴다.
6. **D1 대신 Durable Object.** D1에는 구독이나 변경 피드가 없어서 실시간 전파를 하려면 WebSocket을 받을 DO가 어차피
   필요하다. 이 기기의 보드(할 일 223개, 댓글 265개, 히스토리 2,187행)는 JSON으로 1MB가 안 되어 DO 하나의
   SQLite(객체당 10GB)로 충분하다. Cloudflare도 사용자별 SQL 상태와 실시간 협업에 DO를 권한다.
7. **워커는 TypeScript다.** 보드 규칙은 데몬에만 있고, 워커는 사본·변경함·전파만 다루는 가장자리 코드다. 웹의 낙관적
   반영 모듈을 워커와 같이 쓴다. `workers-rs`는 1.0 전이고, 지금 보드 규칙(`store.rs`)은 SQL에 묶여 있어 wasm으로
   옮기려면 먼저 떼어 내야 한다.
8. **싱크 라이브러리를 들이지 않는다.** 서버를 Rust 데몬으로 둘 수 있는 것은 Replicache 프로토콜 정도인데,
   Replicache는 유지보수 모드다. LiveStore는 데몬이 이벤트 소싱으로 바뀌어야 하고, Zero는 Postgres가 필요하다.
   프레임 모양은 Replicache의 pull·push·poke를 따른다.
9. **웹은 낙관적으로 반영한다.** "서버가 정본"이라는 전제는 그대로 두고, 확정된 행 위에 아직 확인받지 않은 변경을
   겹쳐 그린다. 서버가 거절하면 되돌린다.

## 1번 조각 — 싱크 프로토콜

### 대상 테이블

`boards`, `sections`, `todos`, `comments`, `notes`, `history`, `handoffs` 일곱 개. `note_docs`(CRDT 상태)는 지금의
노트 문서 프레임(`doc`·`update`·`sub`)으로 오가므로 넣지 않는다. 수집함·구독·전달·PR 감시 테이블은 기계 상태라서
넣지 않는다.

행 모양은 지금 타입(`Board`, `Section`, `Todo`, `Comment`, `Note`, `HistoryEntry`, `Handoff`)의 JSON에 `seq`를 더한
것이다. `ref`·`commentCount` 같은 파생 값과 세션에서 계산하는 값(`doingState`, `stale`)은 싣지 않고 클라이언트가
계산한다.

### 순번 `seq`

- `sync_state` 행 하나에 마지막 순번과 `epoch`를 둔다. `epoch`는 스토어가 DB를 열 때마다 새로 정한다(실패 처리 참고).
- 일곱 테이블에 `seq INTEGER NOT NULL DEFAULT 0` 열과 인덱스를 둔다. `AFTER INSERT`·`AFTER UPDATE` 트리거가
  `sync_state.seq`를 1 올리고 그 값을 행에 적는다. `record_history`를 부르는 쓰기 26곳과 그렇지 않은 쓰기를 하나도
  고치지 않아도 모든 변경에 순번이 붙는다.
- 트리거 안의 갱신은 `WHEN NEW.seq IS OLD.seq` 조건과 SQLite 기본값(재귀 트리거 꺼짐) 두 겹으로 자기를 다시 부르지
  않는다.
- 대상 목록은 마이그레이션 19 안에 고정한다. 이미 19까지 간 DB는 그 마이그레이션을 다시 돌지 않으므로, 대상을 늘릴
  때는 새 마이그레이션으로 열과 트리거를 더한다.
- 기존 행은 0으로 둔다. 처음 받는 클라이언트는 늘 통째로 받으므로 소급하지 않아도 된다.
- 삭제가 없다(보관만). 그래서 지운 행을 따로 기억하지 않는다.
- 쓰기는 연결 하나(`Mutex<Connection>`)로 줄을 서므로 순번 순서가 커밋 순서다.

### 깨우기

지금 변경 이벤트(`ChangeEvent`)는 히스토리를 남기는 쓰기에서만 나온다. 그래서 세션 귀속(`claim-session`), 조절된
노트 편집 이벤트, 섹션 보관에 딸린 할 일 보관을 놓친다. 대신 `rusqlite`의 `update_hook`(기능 `hooks`, 새 크레이트가
아니다)으로 대상 테이블이 바뀔 때 스토어가 알린다. 데몬은 알림을 받으면 20ms 모았다가 연결마다 "그 연결에 보낸
순번 이후"를 읽어 보낸다. 방송 채널을 쓰지 않으므로 밀린 연결도 다음 차례에 한꺼번에 받는다(`lag` 없음).

### 프레임 (`GET /api/ws`)

지금의 노트 소켓에 프레임을 더한다. 클라이언트는 연결 하나로 노트 문서와 보드 행을 함께 받는다.

- `{t:"sync", since?, epoch?}` → `{t:"rows", epoch, seq, full, rows:{boards:[…], sections:[…], …}}`
  - `since`가 없거나 음수이거나, `epoch`가 다르거나, `since`가 지금 순번보다 크면 `full:true`다. 클라이언트는 사본을
    통째로 바꾼다. 통째로 줄 때 히스토리는 최근 2,000줄까지만 싣는다(히스토리는 쓰기마다 늘어 끝이 없다). 그보다
    오래된 줄은 REST로 받는다.
  - 그 밖에는 `seq > since`인 행만 보낸다. 이어 받기는 자르지 않는다.
- `sync`를 받은 연결에는 바뀐 행이 생길 때마다 데몬이 같은 `rows` 프레임(`full:false`)을 먼저 보낸다.
- `{t:"tx", id, ops:[…]}` → `{t:"ack", id, seq}` 또는 `{t:"reject", id, at, error}`. 데몬은 `ack` 앞에 그 순번까지의
  `rows`를 먼저 보낸다. 그래서 `ack`를 받은 클라이언트의 사본에는 이미 결과가 들어 있다.

### 트랜잭션

- 어휘는 원격에서도 이미 허용된 보드 쓰기만이다. 할 일 만들기·고치기·상태 바꾸기·순서, 댓글 쓰기·고치기·보관·보관
  풀기, 섹션 만들기·보관, 노트 만들기·제목·보관·보관 풀기·고정·고정 풀기, 보드 제목·설명.
- 트랜잭션은 사람(웹·폰)의 쓰기다. 에이전트 actor면 거절한다. 에이전트의 `start`는 핸드오프를 수락하고 그 앞에서 세션
  목록을 조회(프로세스 실행)하는데, 그 길을 소켓에 열지 않는다. 에이전트는 MCP·REST로 쓴다.
- 세션 띄우기, 이슈 만들기, 핸드오프, 보드의 `path`·`repo`·`reviewFix`·`prAuthors`, 수집함 설정은 어휘에 없다.
  그런 쓰기는 지금처럼 로컬 요청 전용 REST로만 한다. 클라우드를 거쳐 온 쓰기가 프로그램 실행으로 이어질 길이
  프로토콜에 없다.
- op마다 지금 스토어 메서드를 그대로 부른다. 검증(REST 라우트의 검사까지), 히스토리, 이벤트가 REST와 같다. 행위자는
  소켓의 `actor`다.
- 만들기(할 일·노트·댓글)는 클라이언트가 정한 id(`new_id`와 같은 8자 base36)를 받는다. 낙관적으로 그린 행과 확정된
  행의 id가 같고, 응답을 잃어 다시 보내도 두 번 만들어지지 않는다(같은 자리에 같은 id가 있으면 성공, 다른 자리에 있으면
  거절). 섹션은 이름으로 만든다(같은 이름이면 그 섹션).
- 트랜잭션은 원자적이지 않다. op가 하나라도 읽히지 않으면 아무것도 적용하지 않지만, 적용하다 실패하면 그 op에서 멈춘다.
  앞의 op는 남고, `reject`의 `at`이 실패한 op의 자리다. 결과는 어차피 `rows`로 돌아온다. 그래서 클라이언트는 op 하나짜리
  트랜잭션을 기본으로 쓴다.

### 번호

번호는 데몬이 매긴다. 지금 `next_number`는 `MAX(number)+1`이라, 보드에서 가장 큰 번호의 할 일을 다른 보드로 옮기면
원래 보드가 그 번호를 다시 준다. 줄지 않는 보드별 카운터로 바꾼다(1번 조각과 따로 내는 PR).

### 실패 처리

- 연결이 끊기면 클라이언트가 다시 붙어 `sync since=<마지막 seq>`로 이어 받는다.
- 데몬이 다시 뜨면 `epoch`가 바뀌어 클라이언트가 통째로 다시 받는다. DB를 백업에서 되살린 경우도 같다. 같은
  `epoch`로 이어 받으면, 되살린 DB가 새로 매긴 순번과 클라이언트가 가진 옛 순번이 겹쳐 빠진 변경을 알 수 없다. 대가는
  데몬이 다시 뜬 뒤 첫 연결이 통째로 받는 것이다(보드 1MB 미만).
- 트리거가 빠지면 그 테이블의 변경이 퍼지지 않는다. `sync_test`가 실제 DB로 트리거 열네 개를 이름으로 고정한다.

### 검증

- 스토어: 테이블마다 삽입과 수정에 순번이 오르고, `since` 이후의 행만 나온다. 기존 테스트는 그대로 통과한다.
- 소켓: 실제 클라이언트(`tokio-tungstenite`)로 `sync` → 통째 사본 → REST 쓰기 → 밀려온 `rows`, 끊고 `since`로
  다시 붙기, `tx` → `rows` → `ack`.
- 사용 로그: 새 프레임을 `KNOWN_SURFACES`에 넣는다.

## 2번 조각 — 로컬 퍼스트 웹

### 사본에 두는 것

- 일곱 테이블 전부를 웹이 사본으로 갖는다. 화면이 읽는 `boards`·`todos`·`nowTodos`·`sections`·`notes`·`handoffs`·
  `nowHandoffs`와 상세 드로어(연결된 세션 기록 포함)는 사본에서 계산한다. 보드를 바꾸거나 보관 항목 보기를 켜도 요청을
  보내지 않는다.
- 세션 목록, rc, PR 감시, 수집함 요약, 작업로그, `/api/health`는 지금처럼 REST와 폴링으로 받는다. SSE(`/api/events`)는
  PR과 수집함 요약을 다시 읽을 때만 쓴다.
- TUI는 바꾸지 않는다.

### 웹이 계산하는 값

데몬이 응답에 얹던 값을 웹이 같은 규칙으로 계산한다. 데몬 함수를 옮긴 것이라 테스트도 데몬 테스트의 사례를 쓴다.

- `ref`: 보드 key와 번호. key가 참조에 쓸 수 없는 모양이면 id다(`is_ref_safe_board_key`). 보드가 없는 노트는 `note-N`이다.
- `commentCount`·`lastCommentAt`: 그 할 일의 보관하지 않은 댓글 수와 가장 늦은 `createdAt`.
- `doingState`와 핸드오프의 `phase`·`unstarted`·`stale`: 세션 목록(`GET /api/sessions`)으로 `rocky_core::doing`의
  규칙을 따른다. 세션 목록은 에이전트 탭이 이미 15초(탭을 보는 동안)나 60초마다 받는다. 탭을 꺼 둔 화면도 doing인 할
  일이나 열린 핸드오프가 있으면 60초마다 받는다. 목록이 없으면 판정하지 않고 지금처럼 "모름"으로 둔다.
- 판정에 걸리는 행(열린 핸드오프, doing인 할 일)이 바뀌면 세션 목록을 바로 한 번, 3.5초 뒤에 한 번 더 받는다. 데몬의 목록
  캐시는 오래된 값을 바로 주고 뒤에서 새로 받으므로(3초 안이면 그대로) 바뀐 직후의 목록은 그 변화를 모를 수 있다. 그래서
  바뀐 뒤 3.5초가 지나 물은 목록이 올 때까지, 그 사이 바뀐 행(`seq`로 가린다)은 판정하지 않는다. 방금 뜬 세션을 "세션 없음"
  이나 "착수 안 함"으로 그리지 않으려는 것이다.

### 쓰기

- 트랜잭션 어휘에 있는 쓰기(할 일·댓글·섹션·노트, 보드 제목과 설명)는 사본이 데몬을 따라가고 있을 때(`live` — 지금 연결로
  `rows`를 받았다) `tx`로 보낸다. 트랜잭션 하나에 op 하나다. 저장 사본만 그린 채 아직 붙지 못했거나 끊긴 동안의 쓰기는
  REST로 보낸다.
- 보내는 순간 화면에 반영한다. 확정된 행 위에 아직 답을 받지 않은 op를 차례로 겹쳐 그린다. `ack`가 오면 그 op를
  걷는다. 결과 행은 `ack`보다 먼저 와 있다. `reject`면 op를 걷고 부른 쪽에 오류를 돌려준다. 오류는 지금 화면이 보여
  주는 자리에 그대로 나온다.
- 겹쳐 그릴 때 고친 행의 `updatedAt`은 건드리지 않는다. 그 값은 서버 시계다. 노트의 "본 것"은 확정된 행으로만 올린다.
- 만들기는 웹이 id를 정한다(8자 base36). 새 할 일은 데몬이 번호를 줄 때까지 `rocky-?`로 그린다. 그 항목의 주소
  (`/rocky/12`, `/rocky/notes/3`)는 번호를 받은 뒤에 만든다. 만들고 바로 여는 노트는 `ack`를 기다렸다가 연다.
- 막 만든 할 일에 REST로만 하는 동작(보내기, 새 세션, 이슈, 다른 보드로 옮기기)은 데몬이 그 만들기를 확정할 때까지
  기다렸다 보낸다. 데몬이 모르는 id로 나가지 않게 하려는 것이다. 막 만든 노트도 확정된 뒤에 연다.
- 에이전트 actor로 연 화면은 `tx`를 쓰지 않고 REST로 보낸다. 데몬이 에이전트의 `tx`를 거절한다.
- 어휘에 없는 쓰기는 지금처럼 REST로 보낸다. 보드 만들기, 다른 보드로 옮기기, 보드의 key·레포·경로, 이슈, 핸드오프,
  세션 띄우기, 노트 본문(CRDT 편집기)이 그렇다. 응답 뒤에 목록을 다시 읽지 않는다. 결과는 `rows`로 온다.
- 보낼 op와 답을 기다리는 op는 메모리에만 둔다. 로컬 데몬은 수 ms 안에 답한다. 끊긴 동안 쌓인 op는 다시 붙으면
  보낸다. 보냈는데 답을 받기 전에 끊긴 op 가운데 만들기는 다시 보낸다(같은 id라 두 번 생기지 않는다). 나머지는
  적용됐는지 알 수 없으므로 걷고 오류로 돌려준다. 화면은 이어 받은 사본을 따른다. 탭을 닫으면 쌓인 op를 잃는다.
  op를 IndexedDB에 두는 일은 맥이 잠든 동안 쓰는 4번 조각에서 한다.

### 사본 저장 (IndexedDB)

- 데이터베이스 하나에 테이블마다 저장소를 두고 `meta`에 `epoch`·`seq`를 둔다. 부팅하면 사본을 읽어 먼저 그리고,
  소켓이 붙으면 `sync since epoch`로 이어 받는다. cmux가 숨은 패널을 다시 열 때도 네트워크를 기다리지 않는다.
- 사본을 읽는 데는 1초까지만 기다린다. 그보다 늦게 온 사본은 쓰지 않는다. 사본이 있으면 부팅 때 보드 묶음을 REST로
  읽지 않는다. 사본이 없으면(첫 방문) REST로 그리다가 첫 `rows`가 오면 사본으로 넘어간다.
- 저장 사본으로 그렸으면 주소(`/rocky/57`)는 데몬을 따라잡은 뒤에 푼다. 낡은 사본에 없는 새 항목의 링크를 지우지
  않게 하려는 것이다.
- `rows`를 받을 때마다 바뀐 행을 한 트랜잭션으로 쓴다. `full`이면 비우고 다시 쓴다. 저장이 한 번 실패하면 다음 저장은
  사본 전체를 쓴다. 델타만 쓰면 실패한 프레임의 행이 머리(`seq`) 뒤에 숨어 다음 부팅이 그 행을 다시 받지 못한다.
- 저장소를 열지 못하는 브라우저(비공개 창 등)에서는 메모리 사본만으로 돈다. 다른 탭이 새 모양(`DB_VERSION`)으로 열면
  연결을 놓아준다.
- Access로 들어온 화면은 로그아웃할 때 싱크를 멈추고 걸린 저장이 끝난 뒤에 사본을 지운다. 지운 뒤에 온 행이 다시 쓰이지
  않게 하려는 것이다. 폰 브라우저에 보드 사본이 남는 것은 이 조각에서 새로 생기는 일이다.

### 소켓

- 보드 싱크는 노트 편집기와 다른 소켓을 연다. 노트 소켓은 편집기를 열 때만 붙고 보드 소켓은 늘 붙어 있다. 둘을
  하나로 합치는 일은 뒤로 미룬다.
- 끊기면 1·2·4…30초 간격으로 다시 붙는다. 10초 넘게 붙어 있던 연결이 끊겼을 때만 1초부터 다시 센다. 붙자마자 닫는
  프록시 앞에서 1초마다 돌지 않게 하려는 것이다. 화면이 다시 보이면(`visibilitychange`) 바로 붙는다.
- 사본이 데몬을 따라가지 못하는 동안(부팅 직후의 저장 사본, 끊긴 소켓)에도 5초까지는 사본으로 그린다. 그 안에 따라잡지
  못하면 지금 방식(REST, SSE, 60초 다시 읽기)으로 돈다. 소켓은 계속 다시 붙어 보고, 따라잡으면 사본으로 돌아온다. 한 번도
  붙지 못하는 환경(프록시가 막는 등)도 같다.
- 반쯤 죽은 소켓(닫힘이 오지 않는다)은 `ping`으로 가린다. 30초 동안 아무 프레임이 없거나 화면이 다시 보이면 묻고, 5초 안에
  답이 없으면 닫고 다시 붙는다. 데몬에 `{t:"ping"}` → `{t:"pong"}` 프레임을 더한다. 사용 로그는 남기지 않는다(`sync`는
  프레임마다 남기므로 하트비트로 쓰지 않는다).
- `sync`의 읽기가 실패하거나(`id`가 `sync`인 `err`) 데몬이 밀기에 실패하면(`id` 없는 `err`) 커서부터 `sync`를 다시 보낸다.
  5초 안에 또 오면 5초를 채운 뒤에 보낸다.

### 걷는 것

- 보드 묶음(`boards`·`todos`·`notes`·`sections`·`handoffs`)을 다시 읽던 `refetch`, SSE 이벤트마다 하던 다시 읽기,
  60초 전체 다시 읽기. 60초 타이머는 PR·수집함 요약을 다시 읽고 경과 시간 표시를 다시 그리는 데만 남긴다.
- 상세 드로어의 `GET /api/todos/:id`와 연결된 세션의 `GET /api/handoffs?todo=`. 드로어는 사본으로 바로 그린다. 연 순간에
  `GET /api/todos/:id`를 한 번만 보내 2,000줄보다 오래된 히스토리를 채운다. 사본을 받기 전에 REST로 연 상세의 히스토리도
  남긴다.
- 바뀌지 않은 묶음은 같은 배열로 둔다. 노트 본문 편집처럼 잦은 변경이 와도 바뀌지 않은 화면은 다시 그리지 않는다.

### 검증

- 단위: 사본(통째로 받기, 이어 받기, op 겹치기, `ack`·`reject`), 계산 값(데몬 테스트와 같은 사례), 소켓(가짜 소켓으로
  `sync` → `rows` → `tx` → `ack`·`reject`, 끊고 이어 받기, 붙지 못해도 계속 붙어 보기, `ping`, 저장 실패 뒤 통째 저장).
- 스토어: 쓰기가 `tx`로 나가고 목록을 다시 읽지 않는다. 답을 기다리는 op가 겹쳐 그려진다(번호 없는 새 할 일). 따라잡기
  전과 기다려 줄 시간이 지난 뒤의 REST, 막 만든 할 일의 REST 동작 기다리기, 세션 판정 가리기.
- E2E: 다른 곳(REST)에서 만든 할 일이 다시 읽기 없이 밀려온다. 다시 연 화면은 저장한 사본으로 그리고 할 일 목록을
  요청하지 않는다. 화면이 사본으로 그리는지는 `<html data-sync="replica">`로 본다.
- 사용 로그: 웹의 `GET /api/todos`·`/api/notes`·`/api/handoffs` 호출 수를 머지 전후로 잰다.

### PR

`gh stack`으로 다섯을 낸다. ① 이 절 ② 사본 읽기(`web/sync/replica.ts`의 `rows` 적용, `views.ts`의 계산 값)
③ 쓰기 겹치기(`replica.ts`의 op) ④ 소켓과 IndexedDB(`client.ts`·`persist.ts`, 데몬의 `ping`) ⑤ 화면 연결과 다시 읽기
걷기(`store.ts`·`main.tsx`).

## 3·4번 조각 — 클라우드 (개요)

- `cloud/`: Worker(정적 파일, Access 토큰 검증)와 DO 하나(SQLite: 사본·변경함, Hibernation WebSocket).
- 데몬 연결기: `todo.sync`가 있을 때만 뜬다. 데몬 쪽에서는 싱크 프로토콜의 클라이언트이고, 클라우드와도 같은
  프레임을 주고받는다. 기계 필드(`path`, `repo` 등)는 보내지 않는다.
- 노트 문서는 Yjs 동기화 프로토콜로 맥과 주고받는다. 서버 둘 사이에서는 양쪽이 상태 벡터를 먼저 보낸다.
- 클라우드 화면은 피드·할 일·노트만 보인다. 머리줄에 맥 연결 상태와 보낼 변경 개수를 둔다.
- Access: Worker 단위 Access는 2026-10 문서 기준으로 WebSocket을 받지 못한다. 도메인 단위 Access 앱 뒤에 두고
  워커가 JWT를 직접 검증한다(데몬의 `rocky_core::access`와 같은 규칙). 서비스 토큰을 단 WebSocket이 Access를
  통과하는지는 문서에 없어서 3번 조각의 첫 일로 실측한다.
- DO는 배포할 때 WebSocket이 모두 끊긴다. 클라이언트와 연결기가 순번으로 이어 받는다.
- 3번을 설계할 때 정할 것: 올릴 보드(전부 올리고 빼는 보드만 끄기 / 고른 보드만), 폰에서 맥 작업(핸드오프·새 세션)
  예약 여부, 서비스 토큰 보관 위치, 주소.

## 범위 밖

- 데몬을 클라우드로 옮기기. 오프라인에서 보드가 죽는다.
- 기기끼리 보드 맞추기. 기기마다 독립 인스턴스다.
- 클라우드를 거친 맥 작업(세션 띄우기, 핸드오프). 3번 설계 때 따로 정하기 전까지 없다.
- 번호 미리 떼어 주기. 맥이 잠든 동안 만든 할 일은 맥이 깰 때 번호를 받는다.
