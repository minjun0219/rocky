# 이중 구조와 싱크 — 설계 (로컬 데몬 + 클라우드 중계소, Linear식 클라이언트)

- 날짜: 2026-10-15
- 결정자: 오너 (방향: 이 문서의 A안, 로컬 싱크부터)
- 상태: 1·2번 조각은 머지됐다(2026-10-16). 3번 조각은 설계를 더했고 "정한 것" 넷을 오너가 확정했다(2026-10-17).
  3번 조각의 중계소 코어(②)와 Worker·DO 껍데기(③)가 들어갔다. 오너 계정에 배포해 서비스 토큰을 단 업그레이드가
  Access를 지나는 것을 확인했다(2026-10-19, 3번 조각 "인증").
  4번 조각은 중계소 주소 하나로 웹 UI 전체를 열기로 하고(오너 결정, 2026-10-19), 데몬 REST를 중계소로 넘기는 길
  ("데몬에 묻기")을 먼저 적었다. 4번 조각의 "정한 것" 둘도 오너가 확정했다(2026-10-19). 나머지는 시작할 때
  이 문서에 더한다

## 한 줄

**데몬은 계속 그 기기 보드의 정본이다.** 동기화를 켠 기기에서는 Cloudflare의 Durable Object 하나가 중계소가 되어,
맥이 잠든 동안 폰에서 한 쓰기를 받아 두었다가 데몬이 연결되면 넘긴다. 웹 화면은 로컬과 클라우드 모두 Linear처럼
기기에 사본을 두고, 쓰기는 먼저 화면에 반영하고, 바뀐 행만 받는다.

## 왜

- **두 가지 쓰임.** 데스크톱 중심 기기는 지금처럼 맥 안에서만 쓴다. 모바일 중심 기기는 맥이 잠들어 있어도 폰에서
  보드를 보고 고치고 싶다. 지금 원격 접근(Cloudflare Tunnel + Access)은 맥이 깨어 있어야 열린다.
- **웹이 느리다.** 데몬 처리 시간은 이미 짧다. 2026-10-01~15 사용 로그에서 웹이 부른 `GET /api/todos`의 처리 시간은
  p50 8ms다. 느린 곳은 웹이 쓰기마다 서버 확정을 기다리고(`web/store.ts`의 "낙관적 갱신을 하지 않는다"), 이름 없는
  변경 알림(SSE)마다 목록을 통째로 다시 받고, 60초마다 전부 다시 받는 구조다. 같은 기간 웹은 `GET /api/logs/worklog`를
  10,180번, `GET /api/handoffs`를 5,879번 불렀다. 폰에서 터널로 들어오면 이 왕복이 모두 인터넷을 건넌다.
- **Linear의 방식.** Linear는 처음 한 번 데이터를 받아 IndexedDB에 두고, 데이터베이스 전체에 하나뿐인 순번
  (`lastSyncId`) 이후의 변경만 WebSocket으로 받는다. 쓰기는 트랜잭션으로 먼저 화면에 반영하고, 서버가 거절하면
  되돌린다. 충돌은 서버에 도착한 순서로 정하고(필드 단위), CRDT는 긴 글(이슈 설명)에만 쓴다. 이슈 번호는 서버가
  매긴다. rocky도 같은 모양으로 간다.

## 결정

1. **데몬이 정본이다.** 웹·TUI·클라우드는 모두 데몬의 클라이언트다. 번호 매기기와 자동화(PR 감시, 핸드오프,
   doing 귀속)는 데몬만 한다.
2. **클라우드는 중계소다.** Cloudflare Worker와 SQLite Durable Object(DO) 하나. DO에는 데몬이 확정한 행의 사본과,
   데몬이 연결되지 않은 동안 받은 쓰기(보낼 변경함)만 둔다. 데몬이 연결되면 변경함을 넘기고, 데몬이 확정한 행으로
   사본을 바꾼다.
3. **연결은 데몬이 먼저 건다.** 데몬이 바깥으로 WebSocket 하나를 연다(Access 서비스 토큰). 맥에 들어오는 문을 새로
   열지 않는다.
4. **기기별 opt-in.** [`docs/rewrite/decisions.md`](../../rewrite/decisions.md) "확장 경로 제약"(2026-08-31)을
   그대로 따른다. 기본은 로컬 전용이고 설정 키는 그때 비워 둔 `todo.sync`다. 데몬 코어는 클라우드를 모르고, 연결기는
   다른 클라이언트와 같은 싱크 프로토콜로 바뀐 행을 받는다. 동기화를 켜지 않은 기기의 보드 데이터는 어떤 경로로도
   기계를 떠나지 않는다.
5. **충돌은 데몬에 도착한 순서로 정한다.** 쓰기는 필드 단위 패치라서 나중에 도착한 패치의 필드가 남는다. 진 값은
   히스토리에 남는다. 노트 본문은 지금의 CRDT(Yjs)를 그대로 쓴다.
6. **D1 대신 Durable Object.** D1에는 구독이나 변경 피드가 없어서 실시간 전파를 하려면 WebSocket을 받을 DO가 어차피
   필요하다. 이 기기의 보드(할 일 223개, 댓글 265개, 히스토리 2,187행)는 JSON으로 1MB가 안 되어 DO 하나의
   SQLite(객체당 10GB)로 충분하다. Cloudflare도 사용자별 SQL 상태와 실시간 협업에 DO를 권한다.
7. **워커는 TypeScript다.** 보드 규칙은 데몬에만 있고, 워커는 사본·변경함·전파만 다루는 가장자리 코드다. 웹의 낙관적
   반영 모듈을 워커와 같이 쓴다. `workers-rs`는 1.0 전이고, 지금 보드 규칙(`store.rs`)은 SQL에 묶여 있어 wasm으로
   옮기려면 먼저 떼어 내야 한다.
8. **싱크 라이브러리를 들이지 않는다.** 서버를 Rust 데몬으로 둘 수 있는 것은 Replicache 프로토콜 정도인데,
   Replicache는 유지보수 모드다. LiveStore는 데몬이 이벤트 소싱으로 바뀌어야 하고, Zero는 Postgres가 필요하다.
   프레임 모양은 Replicache의 pull·push·poke를 따른다.
9. **웹은 낙관적으로 반영한다.** "서버가 정본"이라는 전제는 그대로 두고, 확정된 행 위에 아직 확인받지 않은 변경을
   겹쳐 그린다. 서버가 거절하면 되돌린다.
10. **동기화를 켠 기기는 밖에서 중계소 주소 하나로 연다.** 터널을 다른 주소에 다시 달지 않는다(오너 결정,
    2026-10-19). 웹이 부르는 데몬 REST는 중계소가 데몬이 연 소켓으로 넘기고, 받을지는 데몬이 정한다(4번 조각).

## 1번 조각 — 싱크 프로토콜

### 대상 테이블

`boards`, `sections`, `todos`, `comments`, `notes`, `history`, `handoffs` 일곱 개. `note_docs`(CRDT 상태)는 지금의
노트 문서 프레임(`doc`·`update`·`sub`)으로 오가므로 넣지 않는다. 수집함·구독·전달·PR 감시 테이블은 기계 상태라서
넣지 않는다.

행 모양은 지금 타입(`Board`, `Section`, `Todo`, `Comment`, `Note`, `HistoryEntry`, `Handoff`)의 JSON에 `seq`를 더한
것이다. `ref`·`commentCount` 같은 파생 값과 세션에서 계산하는 값(`doingState`, `stale`)은 싣지 않고 클라이언트가
계산한다.

### 순번 `seq`

- `sync_state` 행 하나에 마지막 순번과 `epoch`를 둔다. `epoch`는 스토어가 DB를 열 때마다 새로 정한다(실패 처리 참고).
- 일곱 테이블에 `seq INTEGER NOT NULL DEFAULT 0` 열과 인덱스를 둔다. `AFTER INSERT`·`AFTER UPDATE` 트리거가
  `sync_state.seq`를 1 올리고 그 값을 행에 적는다. `record_history`를 부르는 쓰기 26곳과 그렇지 않은 쓰기를 하나도
  고치지 않아도 모든 변경에 순번이 붙는다.
- 트리거 안의 갱신은 `WHEN NEW.seq IS OLD.seq` 조건과 SQLite 기본값(재귀 트리거 꺼짐) 두 겹으로 자기를 다시 부르지
  않는다.
- 대상 목록은 마이그레이션 19 안에 고정한다. 이미 19까지 간 DB는 그 마이그레이션을 다시 돌지 않으므로, 대상을 늘릴
  때는 새 마이그레이션으로 열과 트리거를 더한다.
- 기존 행은 0으로 둔다. 처음 받는 클라이언트는 늘 통째로 받으므로 소급하지 않아도 된다.
- 삭제가 없다(보관만). 그래서 지운 행을 따로 기억하지 않는다.
- 쓰기는 연결 하나(`Mutex<Connection>`)로 줄을 서므로 순번 순서가 커밋 순서다.

### 깨우기

지금 변경 이벤트(`ChangeEvent`)는 히스토리를 남기는 쓰기에서만 나온다. 그래서 세션 귀속(`claim-session`), 조절된
노트 편집 이벤트, 섹션 보관에 딸린 할 일 보관을 놓친다. 대신 `rusqlite`의 `update_hook`(기능 `hooks`, 새 크레이트가
아니다)으로 대상 테이블이 바뀔 때 스토어가 알린다. 데몬은 알림을 받으면 20ms 모았다가 연결마다 "그 연결에 보낸
순번 이후"를 읽어 보낸다. 방송 채널을 쓰지 않으므로 밀린 연결도 다음 차례에 한꺼번에 받는다(`lag` 없음).

### 프레임 (`GET /api/ws`)

지금의 노트 소켓에 프레임을 더한다. 클라이언트는 연결 하나로 노트 문서와 보드 행을 함께 받는다.

- `{t:"sync", since?, epoch?}` → `{t:"rows", epoch, seq, full, rows:{boards:[…], sections:[…], …}}`
  - `since`가 없거나 음수이거나, `epoch`가 다르거나, `since`가 지금 순번보다 크면 `full:true`다. 클라이언트는 사본을
    통째로 바꾼다. 통째로 줄 때 히스토리는 최근 2,000줄까지만 싣는다(히스토리는 쓰기마다 늘어 끝이 없다). 그보다
    오래된 줄은 REST로 받는다.
  - 그 밖에는 `seq > since`인 행만 보낸다. 이어 받기는 자르지 않는다.
- `sync`를 받은 연결에는 바뀐 행이 생길 때마다 데몬이 같은 `rows` 프레임(`full:false`)을 먼저 보낸다.
- `{t:"tx", id, ops:[…]}` → `{t:"ack", id, seq}` 또는 `{t:"reject", id, at, error}`. 데몬은 `ack` 앞에 그 순번까지의
  `rows`를 먼저 보낸다. 그래서 `ack`를 받은 클라이언트의 사본에는 이미 결과가 들어 있다.

### 트랜잭션

- 어휘는 원격에서도 이미 허용된 보드 쓰기만이다. 할 일 만들기·고치기·상태 바꾸기·순서, 댓글 쓰기·고치기·보관·보관
  풀기, 섹션 만들기·보관, 노트 만들기·제목·보관·보관 풀기·고정·고정 풀기, 보드 제목·설명.
- 트랜잭션은 사람(웹·폰)의 쓰기다. 에이전트 actor면 거절한다. 에이전트의 `start`는 핸드오프를 수락하고 그 앞에서 세션
  목록을 조회(프로세스 실행)하는데, 그 길을 소켓에 열지 않는다. 에이전트는 MCP·REST로 쓴다.
- 세션 띄우기, 이슈 만들기, 핸드오프, 보드의 `path`·`repo`·`reviewFix`·`prAuthors`, 수집함 설정은 어휘에 없다.
  그런 쓰기는 지금처럼 로컬 요청 전용 REST로만 한다. 클라우드를 거쳐 온 쓰기가 프로그램 실행으로 이어질 길이
  프로토콜에 없다.
- op마다 지금 스토어 메서드를 그대로 부른다. 검증(REST 라우트의 검사까지), 히스토리, 이벤트가 REST와 같다. 행위자는
  소켓의 `actor`다.
- 만들기(할 일·노트·댓글)는 클라이언트가 정한 id(`new_id`와 같은 8자 base36)를 받는다. 낙관적으로 그린 행과 확정된
  행의 id가 같고, 응답을 잃어 다시 보내도 두 번 만들어지지 않는다(같은 자리에 같은 id가 있으면 성공, 다른 자리에 있으면
  거절). 섹션은 이름으로 만든다(같은 이름이면 그 섹션).
- 트랜잭션은 원자적이지 않다. op가 하나라도 읽히지 않으면 아무것도 적용하지 않지만, 적용하다 실패하면 그 op에서 멈춘다.
  앞의 op는 남고, `reject`의 `at`이 실패한 op의 자리다. 결과는 어차피 `rows`로 돌아온다. 그래서 클라이언트는 op 하나짜리
  트랜잭션을 기본으로 쓴다.

### 번호

번호는 데몬이 매긴다. 예전 `next_number`는 `MAX(number)+1`이라, 보드에서 가장 큰 번호의 할 일을 다른 보드로 옮기면
원래 보드가 그 번호를 다시 줬다. 2026-10-16에 고쳤다(마이그레이션 20·21). 할 일이 보드를 떠날 때 트리거가 그 번호를
`number_counters`에 남기고, 다음 번호는 지금 가장 큰 번호와 그 기록 중 큰 값에 1을 더한다.

### 실패 처리

- 연결이 끊기면 클라이언트가 다시 붙어 `sync since=<마지막 seq>`로 이어 받는다.
- 데몬이 다시 뜨면 `epoch`가 바뀌어 클라이언트가 통째로 다시 받는다. DB를 백업에서 되살린 경우도 같다. 같은
  `epoch`로 이어 받으면, 되살린 DB가 새로 매긴 순번과 클라이언트가 가진 옛 순번이 겹쳐 빠진 변경을 알 수 없다. 대가는
  데몬이 다시 뜬 뒤 첫 연결이 통째로 받는 것이다(보드 1MB 미만).
- 트리거가 빠지면 그 테이블의 변경이 퍼지지 않는다. `sync_test`가 실제 DB로 트리거 열네 개를 이름으로 고정한다.

### 검증

- 스토어: 테이블마다 삽입과 수정에 순번이 오르고, `since` 이후의 행만 나온다. 기존 테스트는 그대로 통과한다.
- 소켓: 실제 클라이언트(`tokio-tungstenite`)로 `sync` → 통째 사본 → REST 쓰기 → 밀려온 `rows`, 끊고 `since`로
  다시 붙기, `tx` → `rows` → `ack`.
- 사용 로그: 새 프레임을 `KNOWN_SURFACES`에 넣는다.

## 2번 조각 — 로컬 퍼스트 웹

### 사본에 두는 것

- 일곱 테이블 전부를 웹이 사본으로 갖는다. 화면이 읽는 `boards`·`todos`·`nowTodos`·`sections`·`notes`·`handoffs`·
  `nowHandoffs`와 상세 드로어(연결된 세션 기록 포함)는 사본에서 계산한다. 보드를 바꾸거나 보관 항목 보기를 켜도 요청을
  보내지 않는다.
- 세션 목록, rc, PR 감시, 수집함 요약, 작업로그, `/api/health`는 지금처럼 REST와 폴링으로 받는다. 사본으로 그리는
  동안 SSE(`/api/events`)는 PR과 수집함 요약을 다시 읽을 때만 쓴다. REST로 도는 동안(아래 "소켓")에는 지금처럼 보드
  묶음까지 다시 읽는다.
- TUI는 바꾸지 않는다.

### 웹이 계산하는 값

데몬이 응답에 얹던 값을 웹이 같은 규칙으로 계산한다. 데몬 함수를 옮긴 것이라 테스트도 데몬 테스트의 사례를 쓴다.

- `ref`: 보드 key와 번호. key가 참조에 쓸 수 없는 모양이면 id다(`is_ref_safe_board_key`). 보드가 없는 노트는 `note-N`이다.
- `commentCount`·`lastCommentAt`: 그 할 일의 보관하지 않은 댓글 수와 가장 늦은 `createdAt`.
- `doingState`와 핸드오프의 `phase`·`unstarted`·`stale`: 세션 목록(`GET /api/sessions`)으로 `rocky_core::doing`의
  규칙을 따른다. 세션 목록은 에이전트 탭이 이미 15초(탭을 보는 동안)나 60초마다 받는다. 탭을 꺼 둔 화면도 doing인 할
  일이나 열린 핸드오프가 있으면 60초마다 받는다. 목록이 없으면 판정하지 않고 지금처럼 "모름"으로 둔다.
- 판정에 걸리는 행(열린 핸드오프, doing인 할 일)이 바뀌면 세션 목록을 바로 한 번, 3.5초 뒤에 한 번 더 받는다. 데몬의 목록
  캐시는 오래된 값을 바로 주고 뒤에서 새로 받으므로(3초 안이면 그대로) 바뀐 직후의 목록은 그 변화를 모를 수 있다. 그래서
  바뀐 뒤 3.5초가 지나 물은 목록이 올 때까지, 그 사이 바뀐 행(`seq`로 가린다)은 판정하지 않는다. 방금 뜬 세션을 "세션 없음"
  이나 "착수 안 함"으로 그리지 않으려는 것이다.

### 쓰기

- 트랜잭션 어휘에 있는 쓰기(할 일·댓글·섹션·노트, 보드 제목과 설명)는 사본이 데몬을 따라가고 있을 때(`live` — 지금 연결로
  `rows`를 받았다) `tx`로 보낸다. 트랜잭션 하나에 op 하나다. 저장 사본만 그린 채 아직 붙지 못했거나 끊긴 동안의 쓰기는
  REST로 보낸다.
- 보내는 순간 화면에 반영한다. 확정된 행 위에 아직 답을 받지 않은 op를 차례로 겹쳐 그린다. `ack`가 오면 그 op를
  걷는다. 결과 행은 `ack`보다 먼저 와 있다. `reject`면 op를 걷고 부른 쪽에 오류를 돌려준다. 오류는 지금 화면이 보여
  주는 자리에 그대로 나온다.
- 겹쳐 그릴 때 고친 행의 `updatedAt`은 건드리지 않는다. 그 값은 서버 시계다. 노트의 "본 것"은 확정된 행으로만 올린다.
- 만들기는 웹이 id를 정한다(8자 base36). 새 할 일은 데몬이 번호를 줄 때까지 `rocky-?`로 그린다. 그 항목의 주소
  (`/rocky/12`, `/rocky/notes/3`)는 번호를 받은 뒤에 만든다. 만들고 바로 여는 노트는 `ack`를 기다렸다가 연다.
- 막 만든 할 일에 REST로만 하는 동작(보내기, 새 세션, 이슈, 다른 보드로 옮기기)은 데몬이 그 만들기를 확정할 때까지
  기다렸다 보낸다. 데몬이 모르는 id로 나가지 않게 하려는 것이다. 막 만든 노트도 확정된 뒤에 연다.
- 에이전트 actor로 연 화면은 `tx`를 쓰지 않고 REST로 보낸다. 데몬이 에이전트의 `tx`를 거절한다.
- 어휘에 없는 쓰기는 지금처럼 REST로 보낸다. 보드 만들기, 다른 보드로 옮기기, 보드의 key·레포·경로, 이슈, 핸드오프,
  세션 띄우기, 노트 본문(CRDT 편집기)이 그렇다. 응답 뒤에 목록을 다시 읽지 않는다. 결과는 `rows`로 온다.
- 보낼 op와 답을 기다리는 op는 메모리에만 둔다. 로컬 데몬은 수 ms 안에 답한다. 끊긴 동안 쌓인 op는 다시 붙으면
  보낸다. 보냈는데 답을 받기 전에 끊긴 op 가운데 만들기는 다시 보낸다(같은 id라 두 번 생기지 않는다). 나머지는
  적용됐는지 알 수 없으므로 걷고 오류로 돌려준다. 화면은 이어 받은 사본을 따른다. 탭을 닫으면 쌓인 op를 잃는다.
  op를 IndexedDB에 두는 일은 맥이 잠든 동안 쓰는 4번 조각에서 한다.

### 사본 저장 (IndexedDB)

- 데이터베이스 하나에 테이블마다 저장소를 두고 `meta`에 `epoch`·`seq`를 둔다. 부팅하면 사본을 읽어 먼저 그리고,
  소켓이 붙으면 `sync since epoch`로 이어 받는다. cmux가 숨은 패널을 다시 열 때도 네트워크를 기다리지 않는다.
- 사본을 읽는 데는 1초까지만 기다린다. 그보다 늦게 온 사본은 쓰지 않는다. 사본이 있으면 부팅 때 보드 묶음을 REST로
  읽지 않는다. 사본이 없으면(첫 방문) REST로 그리다가 첫 `rows`가 오면 사본으로 넘어간다.
- 저장 사본으로 그렸으면 주소(`/rocky/57`)는 데몬을 따라잡은 뒤에 푼다. 낡은 사본에 없는 새 항목의 링크를 지우지
  않게 하려는 것이다.
- `rows`를 받을 때마다 바뀐 행을 한 트랜잭션으로 쓴다. `full`이면 비우고 다시 쓴다. 저장이 한 번 실패하면 다음 저장은
  사본 전체를 쓴다. 델타만 쓰면 실패한 프레임의 행이 머리(`seq`) 뒤에 숨어 다음 부팅이 그 행을 다시 받지 못한다.
- 저장소를 열지 못하는 브라우저(비공개 창 등)에서는 메모리 사본만으로 돈다. 다른 탭이 새 모양(`DB_VERSION`)으로 열면
  연결을 놓아준다.
- Access로 들어온 화면은 로그아웃할 때 싱크를 멈추고 걸린 저장이 끝난 뒤에 사본을 지운다. 지운 뒤에 온 행이 다시 쓰이지
  않게 하려는 것이다. 폰 브라우저에 보드 사본이 남는 것은 이 조각에서 새로 생기는 일이다.

### 소켓

- 보드 싱크는 노트 편집기와 다른 소켓을 연다. 노트 소켓은 편집기를 열 때만 붙고 보드 소켓은 늘 붙어 있다. 둘을
  하나로 합치는 일은 뒤로 미룬다.
- actor를 바꾸면 그 이름으로 보드 소켓을 새로 연다. 소켓의 `actor`는 핸드셰이크 때 정해지고 그 연결의 `tx` 히스토리·사용
  로그의 주인이 된다. 바꾸기 전에 답을 기다리던 op는 거절된다.
- 끊기면 1·2·4…30초 간격으로 다시 붙는다. 10초 넘게 붙어 있던 연결이 끊겼을 때만 1초부터 다시 센다. 붙자마자 닫는
  프록시 앞에서 1초마다 돌지 않게 하려는 것이다. 화면이 다시 보이면(`visibilitychange`) 바로 붙는다.
- 사본이 데몬을 따라가지 못하는 동안(부팅 직후의 저장 사본, 끊긴 소켓)에도 5초까지는 사본으로 그린다. 그 안에 따라잡지
  못하면 지금 방식(REST, SSE, 60초 다시 읽기)으로 돈다. 소켓은 계속 다시 붙어 보고, 따라잡으면 사본으로 돌아온다. 한 번도
  붙지 못하는 환경(프록시가 막는 등)도 같다.
- 반쯤 죽은 소켓(닫힘이 오지 않는다)은 `ping`으로 가린다. 30초 동안 아무 프레임이 없거나 화면이 다시 보이면 묻고, 5초 안에
  답이 없으면 닫고 다시 붙는다. 데몬에 `{t:"ping"}` → `{t:"pong"}` 프레임을 더한다. 사용 로그는 남기지 않는다(`sync`는
  프레임마다 남기므로 하트비트로 쓰지 않는다).
- `sync`의 읽기가 실패하거나(`id`가 `sync`인 `err`) 데몬이 밀기에 실패하면(`id` 없는 `err`) 커서부터 `sync`를 다시 보낸다.
  5초 안에 또 오면 5초를 채운 뒤에 보낸다.

### 걷는 것

- 사본으로 그리는 동안에는 보드 묶음(`boards`·`todos`·`notes`·`sections`·`handoffs`)을 다시 읽던 `refetch`, SSE
  이벤트마다 하던 다시 읽기, 60초 전체 다시 읽기를 하지 않는다. 60초 타이머는 PR·수집함 요약을 다시 읽고 경과 시간 표시를
  다시 그리는 데만 쓴다. REST로 도는 동안(소켓을 쓸 수 없거나 따라잡지 못함)에는 셋 다 지금처럼 돈다 — 그래야 소켓이 막힌
  환경에서도 다른 곳의 변경이 보인다.
- 상세 드로어의 `GET /api/todos/:id`와 연결된 세션의 `GET /api/handoffs?todo=`. 드로어는 사본으로 바로 그린다. 연 순간에
  `GET /api/todos/:id`를 한 번만 보내 2,000줄보다 오래된 히스토리를 채운다. 사본을 받기 전에 REST로 연 상세의 히스토리도
  남긴다.
- 바뀌지 않은 묶음은 같은 배열로 둔다. 노트 본문 편집처럼 잦은 변경이 와도 바뀌지 않은 화면은 다시 그리지 않는다.

### 검증

- 단위: 사본(통째로 받기, 이어 받기, op 겹치기, `ack`·`reject`), 계산 값(데몬 테스트와 같은 사례), 소켓(가짜 소켓으로
  `sync` → `rows` → `tx` → `ack`·`reject`, 끊고 이어 받기, 붙지 못해도 계속 붙어 보기, `ping`, 저장 실패 뒤 통째 저장).
- 스토어: 쓰기가 `tx`로 나가고 목록을 다시 읽지 않는다. 답을 기다리는 op가 겹쳐 그려진다(번호 없는 새 할 일). 따라잡기
  전과 기다려 줄 시간이 지난 뒤의 REST, 막 만든 할 일의 REST 동작 기다리기, 세션 판정 가리기.
- E2E: 다른 곳(REST)에서 만든 할 일이 다시 읽기 없이 밀려온다. 다시 연 화면은 저장한 사본으로 그리고 할 일 목록을
  요청하지 않는다. 화면이 사본으로 그리는지는 `<html data-sync="replica">`로 본다.
- 사용 로그: 웹의 `GET /api/todos`·`/api/notes`·`/api/handoffs` 호출 수를 머지 전후로 잰다.

### PR

`gh stack`으로 다섯을 낸다. ① 이 절 ② 사본 읽기(`web/sync/replica.ts`의 `rows` 적용, `views.ts`의 계산 값)
③ 쓰기 겹치기(`replica.ts`의 op) ④ 소켓과 IndexedDB(`client.ts`·`persist.ts`, 데몬의 `ping`) ⑤ 화면 연결과 다시 읽기
걷기(`store.ts`·`main.tsx`).

## 3번 조각 — 클라우드 중계소

### 한 줄

데몬이 바깥으로 소켓 하나를 열어 중계소(Durable Object)에 확정한 행을 밀고, 폰은 중계소에 붙어 웹이 지금 데몬과
쓰는 프레임 그대로 받고 쓴다. 맥이 잠든 동안 폰이 보낸 쓰기는 중계소의 변경함에 쌓였다가, 데몬이 다시 붙으면
도착한 순서대로 데몬에 넘어간다.

```
폰(웹)  --wss /api/ws (Access 로그인)-------> Worker --> 중계소 DO
데몬    --wss /relay  (Access 서비스 토큰)--> Worker --> 중계소 DO
```

연결은 둘 다 Worker 쪽으로 연다. 데몬은 전송으로는 소켓 클라이언트지만 프로토콜로는 지금의 `/api/ws`와 같은
서버다. 중계소가 데몬에 `sync`와 `tx`를 보내고, 데몬이 `rows`와 `ack`·`reject`로 답한다. 그래서 데몬 쪽은
`rockyd::ws`의 보드 싱크 처리를 그대로 쓰고, 거르기와 actor만 다르다.

### 정한 것 (2026-10-17 오너 확정)

| # | 정한 것 | 결정 | 고르지 않은 안 |
| --- | --- | --- | --- |
| 1 | 올릴 보드 | 고른 보드만 올린다(`todo.sync.boards`). 회사 일 보드가 실수로 올라가지 않는다. 보드 없는 노트는 올린다 | 전부 올리고 뺄 보드만 적는다(`todo.sync.exclude`) |
| 2 | 폰에서 맥 작업 예약 | 이 조각에서는 하지 않는다. 트랜잭션 어휘(`SyncOp`)를 늘리지 않는다 | 핸드오프·새 세션을 변경함에 예약한다 |
| 3 | 서비스 토큰 보관 | macOS 키체인(`security find-generic-password`). 환경 변수(`secretEnv`)가 있으면 그쪽을 먼저 쓴다. statusline 토큰과 같은 방식이다 | `~/.config/rocky/` 아래 0600 파일 |
| 4 | 주소 | 설정(`todo.sync.url`)에 적는다. 코드는 주소를 모른다 | |

키체인이 잠겨 있어 비밀을 읽지 못하면 연결하지 않고 `/api/health`에 이유를 남긴다.

### 인증

- Worker는 도메인 단위 Access 앱 뒤에 둔다. Worker 단위 Access는 2026-10 문서 기준으로 WebSocket을 받지 못한다.
- Worker가 `Cf-Access-Jwt-Assertion`을 직접 검증한다. 규칙은 `rocky_core::access`와 같다(RS256, 팀 공개키,
  `iss`·`aud`·`exp`·`nbf`, 60초 허용).
  - 폰(`/api/ws`): 토큰의 `email`이 허용 목록에 있어야 한다.
  - 데몬(`/relay`): 서비스 토큰으로 받은 토큰에는 `email`이 없고 `common_name`에 Client ID가 실린다. 설정한
    Client ID와 같아야 한다.
  - 사람 토큰으로 `/relay`에, 서비스 토큰으로 `/api/ws`에 온 것은 소켓을 열지 않는다.
  - 폰 소켓은 같은 출처의 페이지가 연 것만 받는다. 데몬의 `is_same_origin_request`와 같은 규칙이다. 웹소켓에는
    CORS가 없고, Access 쿠키는 같은 등록 도메인의 다른 서브도메인 페이지가 연 소켓에도 실려 온다. 그래서 폰 화면은
    중계소와 같은 주소에서 낸다(4번 조각)(③).
- **첫 일은 실측이다.** 서비스 토큰 헤더(`CF-Access-Client-Id`·`CF-Access-Client-Secret`)를 단 WebSocket 업그레이드가
  Access를 지나 Worker에 토큰을 달고 오는지 본다. 문서는 "모든 HTTP 요청에 헤더를 단다"고만 한다. 지나지 못하면
  `/relay`만 Access Bypass 정책으로 열고, Worker가 데몬의 서명(HMAC, 비밀은 Worker secret과 데몬 키체인에 하나씩)을
  검증한다. 절차는 `docs/features/sync.md`의 "배포와 실측"이고, 결과는 이 줄 아래에 적는다.
  - 결과(2026-10-19): **지난다.** 서비스 토큰 헤더만 단 보통 GET은 Worker의 426 JSON을 받았다(토큰과 Service Auth
    정책이 맞다). 이어서 보낸 업그레이드는 `101 Switching Protocols` 뒤에 `{"t":"sync","id":"sync"}`를 받았다.
  - 데몬 연결기(④)는 서비스 토큰으로 붙는다. Bypass 정책과 HMAC 서명은 만들지 않는다.
  - 첫 시도는 `ACCESS_AUD`에 다른 Access 앱의 AUD를 넣은 탓에 Worker가 403(`aud`가 다르다)으로 거절했다. Worker의
    `aud` 검사가 실제 Access 토큰에서도 동작한다.
- 브라우저의 WebSocket은 터널 + Access로 `/api/ws`를 써 왔으므로 따로 재지 않았다. 중계소 주소에서는 토큰 없이 보낸
  `/api/ws` 업그레이드가 Access 로그인으로 가는 302를 받는 것만 봤다.

### 중계소가 드는 것

DO 하나(SQLite)에 넷을 둔다. 중계소는 행을 해석하지 않는다. 보드 규칙은 데몬에만 있다.

- `mirror(tbl, id, seq, body)`: 데몬이 보낸 행을 JSON 그대로. 히스토리는 최근 2,000줄로 자른다(데몬이 통째로 줄
  때와 같은 수).
- `meta`: 데몬의 `epoch`, 사본 세대(`generation`), 머리 순번, 지금 데몬 연결.
- `outbox`: 폰이 보낸 op를 도착 순서로. 변경함 id는 중계소가 정한 무작위 값이다. 그 op를 보낸 폰 연결과 폰의
  `tx` id, 지금 답을 기다리는 데몬 연결을 같이 둔다.
- `failed`: 데몬이 거절한 변경함 op 최근 100개. 4번 조각 화면이 보여 준다.

중계소가 폰에 주는 `epoch`는 `<데몬 epoch>.<세대>`다. 데몬에게 통째 사본을 받을 때마다 세대를 올린다. 거르기 때문에
사본에서 빠지는 행이 생기는데(아래 "거르기"), 삭제 프레임이 없으니 폰도 통째로 다시 받아야 그 행이 사라진다.

### 데몬과 중계소 사이

데몬이 붙으면 이렇게 주고받는다.

1. 중계소가 `{t:"sync", id:"sync", since, epoch}`를 보낸다. 값은 자기 사본의 머리(데몬 `epoch`와 순번)다. 사본이
   비어 있으면 둘 다 뺀다.
2. 데몬은 지금 `/api/ws`처럼 `rows`로 답하고, 그 뒤로 행이 바뀔 때마다 `rows`를 민다. 보내기 전에 거른다.
3. 중계소는 변경함의 op를 `{t:"tx", id, actor, ops}`로 하나씩 보내고, 답을 받아야 다음을 보낸다. 도착 순서가 충돌
   규칙이고(결정 5), 끊겼을 때 답을 모르는 op가 하나뿐이어야 한다.
4. 데몬은 `apply_sync_op(op, actor)`로 적용하고 결과 행을 먼저 민 뒤 `ack`·`reject`로 답한다. 지금 소켓과 같다.
5. 중계소는 답을 받으면 그 op를 변경함에서 지운다. 거절이면 `failed`에 남긴다. 그 op를 보낸 폰 연결이 아직 붙어
   있으면 폰의 `tx` id로 같은 답을 전한다.

데몬 쪽에서 지금 소켓과 다른 것:

- **actor**: 지금 소켓은 핸드셰이크의 `actor`로 쓴다. 중계소 연결은 `tx`마다 `actor`(폰의 actor)를 싣는다.
  에이전트 actor면 거절한다(지금 규칙).
- **한 번만 적용한다.** 답을 잃은 변경함 op는 다시 온다. 만들기는 클라이언트 id라 괜찮지만, 상태 바꾸기를 두 번
  적용하면 그 사이 맥에서 한 변경을 덮는다(폰의 "완료"가 맥에서 다시 연 할 일을 또 닫는다). 그래서 데몬이 적용한
  변경함 id와 답을 남긴다(새 테이블 `relay_ops`, 30일). 같은 id가 다시 오면 적용하지 않고 남긴 답을 준다. 적용과
  기록 사이에 데몬이 죽으면 한 번 더 적용될 수 있는데, 그 틈은 받아들인다.
- **거르기**(보내기 전):
  - 올리지 않는 보드의 행: 그 보드의 섹션·할 일·노트, 그 할 일의 댓글·핸드오프, 그것들의 히스토리. 히스토리는
    `entity`(board·section·todo·note)와 `entityId`로 보드를 찾는다. 댓글과 핸드오프의 히스토리는 할 일 아래에 남는다.
  - 기계 필드: 보드의 `path`·`reviewFix`·`prAuthors`, 핸드오프의 `sessionCwd`, 히스토리 `changes` 안의 같은 필드.
    보드의 `repo`는 남긴다. 클라우드 화면의 GitHub 탭과 피드가 보드의 레포로 PR을 고른다(4번 조각).
  - 할 일이 올리는 보드와 올리지 않는 보드 사이를 옮기면 그 뒤 첫 `rows`를 통째로 보낸다. 나간 할 일은 사본에서
    지워야 하고, 들어온 할 일은 예전 댓글·히스토리가 함께 가야 하는데, 순번 이어 받기로는 둘 다 안 된다. 보드
    옮기기는 드물다. 연결기는 할 일마다 마지막으로 본 보드를 기억해 옮김을 알아챈다.

### 폰과 중계소 사이

- 웹이 데몬과 쓰는 프레임 그대로다(`sync`·`rows`·`tx`·`ack`·`reject`·`ping`·`pong`). `web/sync/client.ts`가 그대로
  붙는다. 폰 소켓은 같은 출처의 페이지만 받으므로("인증") 폰 화면을 중계소 주소에서 내고, 소켓 주소는 지금처럼 페이지
  주소에서 나온다(`web/sync/boot.ts`). 터널 주소에서 뜬 화면은 중계소에 붙지 못한다(③).
- `sync`: 중계소 사본의 머리로 `needs_full`과 같은 규칙을 쓴다. 데몬에게 `rows`를 받으면 붙어 있는 폰마다 그 연결의
  커서 이후를 민다. 커서는 소켓 첨부(`serializeAttachment`)에 두어 DO가 잠들었다 깨도 남는다.
- 사본이 비어 있으면(데몬이 한 번도 붙지 않았다) `sync`에 답하지 않고 기다렸다가, 데몬의 첫 행이 오면 통째로 민다.
  빈 `rows`로 답하면 웹은 따라잡았다고 보고 빈 보드를 그린다.
- `tx`: op 이름을 읽어 보고, `ops`가 비었거나 모르는 op거나 에이전트 actor면 `reject`한다. 나머지는 변경함에 넣는다.
  같은 만들기(op 종류와 id가 같다. 섹션은 보드와 이름이 같다)가 이미 변경함에 있으면 다시 넣지 않고, 답을 받을 폰
  연결만 바꾼다. 웹은 끊겼다 붙으면 만들기를 다시 보낸다. 변경함이 1,000개면 받지 않는다.
- 답은 데몬이 적용한 뒤에 간다. 맥이 깨어 있으면 바로 오고, 잠들어 있으면 깰 때까지 늦다. 그동안 웹은 그 op를 답을
  기다리는 op로 겹쳐 그린다(지금 동작). 폰 소켓이 끊기면 웹은 만들기만 다시 보내고 나머지는 "확인하지 못했다"로
  걷는다. 그래도 op는 변경함에 남아 맥이 깨면 적용된다. 변경함을 화면에 보이는 일은 4번 조각에서 한다.
- `ping`은 DO를 깨우지 않는다. `{"t":"ping"}`에 `{"t":"pong"}`을 자동으로 답한다(`setWebSocketAutoResponse`). 웹은
  이 문자열을 그대로 보낸다.

### 노트

- 중계소가 노트마다 Yjs 문서 상태를 SQLite에 둔다. 폰의 `doc`·`update`·`sub`·`presence`에는 지금 데몬과 같은
  프레임으로 중계소가 답한다.
- 데몬과는 Yjs 동기화 규칙으로 맞춘다. 붙을 때 중계소가 노트마다 상태 벡터를 보내 모자란 부분을 받고, 데몬의 상태
  벡터로 자기 쪽 부분을 보낸다. 그 뒤로 데몬은 모든 노트의 편집을 중계소 연결로 밀고, 중계소는 폰의 편집을 데몬에
  보낸다. 데몬이 없을 때 온 편집은 중계소 문서에 쌓였다가 다음 교환 때 넘어간다.
- Worker에 `yjs`가 들어간다. 웹이 이미 쓰는 패키지다.

### 데몬 연결기

- `todo.sync`가 있을 때만 뜬다(`rockyd::relay`). `rocky-core`는 중계소를 모른다.
- 끊기면 1·2·4…60초 간격으로 다시 붙는다. 30초 동안 프레임이 없으면 `ping`을 보내고, 10초 안에 답이 없으면 끊고 다시
  붙는다. 맥이 잠들었다 깨면 소켓이 닫힘 없이 죽어 있다. `ping`은 `{"t":"ping"}` 문자열 그대로 보내 DO의 자동 응답이
  받게 한다.
- 상태는 `/api/health`의 `relay`(붙었나, 언제부터, 마지막 오류)와 `rocky doctor`가 보인다.
- 사용 로그: 연결과 받은 `tx`.
- 새 런타임 의존성: 지금 테스트 전용인 `tokio-tungstenite`를 런타임으로, TLS 기능(`rustls-tls-webpki-roots`)과 함께
  쓴다. `rustls`와 `webpki-roots`는 이미 의존 그래프에 있다. 연결기 PR에서 오너가 정한다.

### 설정

`rocky.json` 사용자 설정의 `todo.sync`. `access` 블록처럼 사용자 설정에서만 읽는다. 프로젝트 설정은 레포에 커밋될 수
있다.

```jsonc
{
  "todo": {
    "sync": {
      "url": "wss://relay.example.com/relay",
      "boards": ["rocky", "home"],
      "clientId": "<서비스 토큰 Client ID>",
      "keychainService": "rocky-sync",
      "secretEnv": "ROCKY_SYNC_SECRET"
    }
  }
}
```

`url`, `clientId`, 비밀 가운데 하나라도 없으면 연결기는 뜨지 않는다. Worker 설정은 secret 넷이다(`ACCESS_TEAM`,
`ACCESS_AUD`, `ACCESS_EMAILS`, `DAEMON_CLIENT_ID`). 레포가 공개라 `cloud/wrangler.jsonc`에는 개인 값과 주소를 적지 않는다(③).

### 실패 처리

- 데몬이 다시 뜨면 `epoch`가 바뀌어 중계소가 사본을 통째로 바꾸고 세대를 올린다. 폰도 통째로 받는다.
- 데몬이 통째가 아닌 `rows`를 다른 `epoch`로 보내면(있어서는 안 된다) 중계소는 그 프레임을 버리고 `since` 없이
  `sync`를 다시 보낸다.
- 데몬이 `err`를 보내면(읽기 실패로 밀기를 멈췄다) 중계소는 그 연결을 닫는다. 연결기가 간격을 두고 다시 붙는다.
  바로 `sync`를 다시 보내면 같은 실패가 쉬지 않고 되풀이될 수 있다.
- 새 데몬 연결이 오면 옛 연결을 닫는다. 답을 기다리던 op는 새 연결로 다시 보낸다(`relay_ops`가 두 번 적용을 막는다).
- 중계소를 배포하면 소켓이 모두 끊긴다. 연결기와 폰이 다시 붙어 순번으로 이어 받는다. 사본과 변경함은 SQLite에
  남는다.
- 맥이 오래 잠들면 변경함이 쌓인다. 1,000개가 차면 폰의 `tx`를 거절한다.
- 변경함 op를 데몬이 거절하면(그 사이 맥에서 보관한 할 일을 폰이 고쳤다) `failed`에 남는다. 그 폰이 붙어 있으면
  `reject`가 그대로 간다.
- 맥이 잠든 동안 폰이 보는 보드는 맥이 마지막으로 보낸 상태다. 폰에서 만든 할 일의 번호는 맥이 깨야 붙고, 히스토리의
  시각도 맥이 적용한 시각이다.

### 이 조각만으로 되는 것

폰 화면은 4번 조각에서 맞춘다. 지금 웹은 부팅 때와 여러 탭에서 데몬 REST(세션·rc·PR·수집함·작업로그)를 부르는데
중계소에는 그 길이 없다. 그 길은 4번 조각에서 연다("데몬에 묻기"). 3번 조각은 중계소와 연결기까지이고, 테스트와
실측으로 확인한다.

### 검증

- 중계소(순수): 통째로 받기·이어 받기·세대, 폰 커서와 밀기, 변경함의 순서·한 번에 하나·답 전달·같은 만들기·상한,
  거절 기록. DO의 SQL은 `bun:sqlite`로 흉내 낸다.
- Worker: Access 토큰 검증(사람·서비스 토큰·다른 길)과 라우팅.
- 데몬: 거르기(보드·기계 필드·히스토리 `changes`), 보드 옮기기 뒤 통째로, `relay_ops`로 한 번만 적용, 연결 위 `tx`의
  actor. 가짜 중계소(axum 소켓 서버)로 연결기를 두드린다.
- 실측: 서비스 토큰을 단 WebSocket이 Access를 지나는지(첫 일).

## 4번 조각 — 클라우드 화면

### 한 줄

터널을 다른 주소에 다시 달지 않고, 중계소 주소 하나로 웹 UI 전체를 연다(오너 결정, 2026-10-19). 보드는 중계소
사본으로 그린다. 맥이 잠들어도 보이고, 어휘에 있는 쓰기(할 일·댓글·섹션·노트)는 변경함에 쌓인다. 웹이 데몬 REST로
받던 것(세션 목록, rc, PR 감시, 수집함, 작업로그)은 중계소가 그 요청을 데몬이 연 소켓으로 넘긴다("데몬에 묻기").
그 부분은 맥이 붙어 있을 때만 보이고, 원격 제어 탭도 그 길로 연다.

### 화면 (개요)

- 머리줄에 맥 연결 상태와 보낼 변경 개수를 둔다. 맥 연결 상태는 폰 소켓으로 알린다.
- 화면은 중계소 주소에서 낸다. 폰 소켓은 같은 출처의 페이지만 받는다(3번 조각 "인증"). 어떻게 낼지는 이 조각에서
  정한다.
- 중계소는 터널이 쓰던 주소를 받았다(오너 결정, 2026-10-19). 그 주소의 Access 앱이 중계소 앞에 선다. 이 조각이 그
  주소에서 화면을 내기 전까지는 밖에서 웹 UI가 열리지 않는다.
- 보드는 사본으로만 그린다. 사본이 따라잡지 못해도 REST로 넘어가지 않고 저장 사본을 그린다. 보드 쓰기는 모두 `tx`로
  보내고, 보낼 op를 IndexedDB에 남긴다(2번 조각 "쓰기"의 마지막 항목).
- 클라우드 화면의 사본은 다른 IndexedDB 이름으로 둔다. 같은 주소에서 터널로 받은 옛 사본(`rocky-sync`)에는 올리지
  않는 보드와 기계 필드가 들어 있다. 그 사본은 그리지 않고 지운다.
- 에이전트 actor로는 보드를 쓰지 못한다. 중계소가 에이전트 actor의 `tx`를 거절하고 보드 REST는 넘기지 않는다. 그래서
  에이전트 actor로 연 클라우드 화면(같은 주소에 남은 설정 포함)은 보드를 읽기만 하고, 사람 actor로 바꾸라고 보인다.
- 변경함을 화면에 보인다. 중계소가 `{t:"outbox"}`로 변경함과 거절된 op를 알린다.
- 클라우드 화면에서 하지 않는 것: 올리지 않는 보드 보기("정한 것" 1), 어휘에 없는 보드 쓰기(보드 만들기, 다른 보드로
  옮기기), 중계소 사본의 2,000줄보다 오래된 히스토리 채우기, SSE(`/api/events`) 열기. PR(`GET /api/prs`)과
  수집함(`GET /api/inbox`)은 60초 타이머로 다시 읽는다. 보드별 PR은 사본에 남긴 보드의 `repo`로 고른다(3번 조각
  "거르기"). 로컬 전용 동작(세션 띄우기, 이슈, 핸드오프)은 지금 터널로 연 화면처럼 꺼진다.
- 홈 화면 앱(PWA).

### 데몬에 묻기

지금 웹은 부팅 때와 여러 탭에서 데몬 REST를 부른다(3번 조각 "이 조각만으로 되는 것"). 중계소가 그 요청을 데몬이 연
`/relay` 소켓에 실어 넘기고 답을 돌려준다. 맥에 들어오는 문은 여전히 없다(결정 3). 3번 조각의 연결기(④) 위에 선다.

```
폰(웹)  --https /api/*  (Access 로그인)--> Worker --> 중계소 DO --{t:"req"}--> 데몬
                                                              <--{t:"res"}--
```

프레임은 둘이다.

- 중계소 → 데몬 `{t:"req", id, method, path, headers, body?}`. `path`는 쿼리까지 담고, 본문은 웹이 보낸 JSON
  문자열이다. `headers`에는 아래 헤더만 옮긴다.
  - 폰의 요청에서 옮기는 것: `cf-access-jwt-assertion`, `sec-fetch-site`, `origin`, `host`, `content-type`,
    `x-rocky-actor`.
  - 중계소가 채우는 것: `cf-access-authenticated-user-email`. 중계소가 검증한 토큰의 `email`이다. 웹이 로그아웃 링크를
    그릴지 정하는 힌트이고 권한 판정에는 쓰지 않는다.
- 데몬 → 중계소 `{t:"res", id, status, body}`. 본문은 데몬 REST의 JSON 그대로다.
- `id`는 중계소가 정한 무작위 값이다. `req`는 변경함을 거치지 않으므로 `tx`가 답을 기다리는 동안에도 오간다.

요청은 폰 소켓에 싣지 않고 HTTP로 받는다. 웹의 REST 호출(`web/store.ts`의 `api`)을 그대로 쓸 수 있고, HTTP 요청에는
Access가 그때의 토큰을 단다. 소켓에 실으면 업그레이드 때 받은 토큰 하나로 버텨야 해서, 그 토큰이 끝나면 원격 제어가
닫힌다.

데몬 쪽:

- `req`를 REST 요청과 같은 문(`handle_api`)으로 받되 들어온 길을 "중계소"로 둔다.
- 중계소 요청은 로컬이 아니다. 헤더와 관계없이 로컬 판정(`is_local_request`)은 거짓이다. 연결기는 데몬 안에서 돈다.
  그 요청을 루프백 요청처럼 넘기면 로컬 전용 라우트가 모두 열린다. 테스트가 이 경계를 고정한다.
- 원격 제어는 지금 규칙을 그대로 쓴다(`docs/features/security.md`의 "예외 — Access 원격 제어"). 판정의 "peer가 루프백
  (cloudflared)" 자리에만 "중계소 연결"이 들어간다. 옮겨 온 `Cf-Access-Jwt-Assertion`을 팀 공개키로 검증하고
  `iss`·`aud`·`exp`·`nbf`·허용 이메일을 본다. 변경은 옮겨 온 `Sec-Fetch-Site`·`Origin`·`Host`로 보아 같은 출처일 때만
  받는다. 중계소도 Access 토큰을 보지만 판정은 데몬이 다시 한다.
- 데몬의 `access` 블록이 중계소 주소의 Access 앱을 가리켜야 한다. `aud`에 그 앱의 AUD(Worker의 `ACCESS_AUD`와 같은
  값)가 없으면 원격 제어가 닫힌다(fail-closed). 터널 앞에 섰던 앱의 AUD만 남아 있으면 그렇다(3번 조각 "인증"의 첫
  시도와 같은 까닭). `aud`는 목록도 받으므로 두 앱을 함께 적을 수 있다.
- 중계소 요청이 닿는 라우트는 아래 묶음뿐이고, 나머지는 404다. 판정은 `rocky-core`의 순수 함수로 두고 테스트가 목록을
  고정한다. 새 라우트는 이 목록에 넣어야 클라우드에서 닿는다.
  - 공통: `GET /api/health`, `POST /api/usage`
  - 에이전트: `GET /api/sessions`
  - 원격 제어: `GET /api/rc/servers`, 원격 제어 등급의 변경(서버 띄우기·재시작, 핸드오프·대상 밖 서버 닫기, 야간 실행)
  - PR 감시: `GET /api/prs`, `GET /api/prs/open`
  - 작업로그: `GET /api/logs/worklog`, `GET /api/logs/stats`
  - 수집함: `GET /api/inbox`
- 보드 REST(보드·섹션·할 일·댓글·노트·핸드오프)와 `GET /api/summary`는 목록에 없다. 요약은 `cwd`가 없으면 모든 보드의
  할 일을 싣는다. 클라우드 화면의 보드는 사본과 변경함으로만 오가므로 올리지 않는 보드("정한 것" 1)가 이 길로 새지
  않는다. 피드가 요약에서 받던 수집함 항목은 클라우드 화면에서 `GET /api/inbox`로 받는다.
- `req`는 따로 처리한다. 느린 답(세션 목록, 수집함 어댑터)이 `rows` 밀기와 `tx`를 막지 않는다.
- 사용 로그는 지금 REST처럼 남기되 중계소를 거친 요청을 가린다. 클라우드 화면이 무엇을 쓰는지 `rocky usage`로 본다.

중계소 쪽:

- Worker는 `/api/ws`를 뺀 `/api/*`의 보통 요청을 받는다. 허용 이메일의 사람 토큰만 들이고, 변경 메서드는 같은 출처만
  받는다(폰 소켓과 같은 `isSameOrigin`). `/api/ws`와 `/relay`는 지금처럼 업그레이드만 받는다.
- DO는 데몬이 붙어 있지 않으면 바로 503으로 답한다. 기다리거나 쌓지 않는다. 맥이 깬 뒤에 원격 제어가 늦게 실행되면
  안 된다(3번 조각 "정한 것" 2).
- 데몬이 붙어 있으면 `req`를 보내고 받은 `res`로 답한다. 30초 안에 답이 없으면 504, 기다리는 동안 데몬 연결이 끊기거나
  바뀌면 502다. 다시 보내지 않는다.
- 기다리는 요청은 그 HTTP 요청이 걸려 있는 동안만 DO 메모리에 둔다. `docs/features/sync.md`의 "상태는 SQLite와 소켓
  첨부에만" 규칙의 예외다. DO가 다시 뜨면 걸린 요청은 실패로 끝난다.
- 답을 저장하지 않는다. 사본의 거르기(올리지 않는 보드, 기계 필드)는 중계소에 남는 것의 규칙이다. 이 길로는 터널로
  보던 답이 그대로 지나고, 세션의 작업 폴더 같은 기계 값도 들어 있다("정한 것" 2).

경계:

- GitHub 쓰기·프로세스 실행·세션 조종은 로컬 요청 전용이고 예외는 원격 제어 탭 하나다(AGENTS.md의 보안 줄). 이
  경계를 그대로 둔다. 이 길은 트랜잭션 어휘(`SyncOp`)를 늘리지 않는다.
- 터널 길은 그대로 둔다. 동기화를 켜지 않은 기기는 지금처럼 터널로 연다. 원격 제어 판정은 루프백(cloudflared)과
  중계소 연결 두 길을 받는다.
- 구현 PR은 README, `docs/features/security.md`·`docs/features/sync.md`, AGENTS.md의 보안 줄에 이 길을 더한다.

### 검증

- 데몬: 중계소 요청은 프록시 헤더가 없어도 로컬이 아니다. 목록 밖 라우트는 404다. 원격 제어는 검증된 토큰과 같은
  출처일 때만 열린다(토큰 없음, 다른 앱의 `aud`, 다른 출처는 닫힌다). `rcControlAllowed`가 옮겨 온 토큰으로 정해진다.
  가짜 중계소(3번 조각 "검증")로 `req` → `res`를 두드린다.
- 중계소(순수): 데몬이 없으면 503, 답이 없으면 504, 끊기면 502이고 다시 보내지 않는다. `req`가 변경함의 순서를
  건드리지 않는다.
- Worker: 사람 토큰만 들이고, 변경은 같은 출처만 받는다. `/api/ws`와 `/relay`는 그대로다.
- 웹: 터널 시절 사본이 남은 브라우저로 클라우드 화면을 열면 그 사본을 그리지 않고 지운다. 에이전트 actor면 보드를
  읽기만 한다. 보드를 고른 GitHub 탭이 사본의 `repo`로 그 보드의 PR을 보인다.
- 실측: 폰에서 원격 제어 탭으로 rc 서버를 다시 띄운다. 큰 답(작업로그 목록 등)이 프레임 하나로 지난다. 요청을
  기다리는 동안 DO가 잠들어 답을 잃지 않는다.

## 범위 밖

- 데몬을 클라우드로 옮기기. 오프라인에서 보드가 죽는다.
- 기기끼리 보드 맞추기. 기기마다 독립 인스턴스다.
- 클라우드를 거친 맥 작업. 변경함에 맥 작업을 예약하지 않고(3번 조각 "정한 것" 2), 세션 띄우기·핸드오프는
  로컬 전용이다. 원격 제어 탭만 맥이 붙어 있을 때 바로 하고 쌓지 않는다(4번 조각 "데몬에 묻기").
- 번호 미리 떼어 주기. 맥이 잠든 동안 만든 할 일은 맥이 깰 때 번호를 받는다.
