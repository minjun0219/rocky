# spec-check — 요구사항 대비 점검

이 변경이 **요청받은 것을 했는가**만 본다. 버그·품질은 기본 `/code-review` 가 같은 diff 를 따로 본다 —
여기서 겹쳐 보지 않는다. 판정은 `reviewer` 서브에이전트(`agents/reviewer.md`)가 새 컨텍스트에서 하고, 이 커맨드는
그 리뷰어에게 넘길 것을 모은다. 읽기만 한다 — 파일을 고치지 않는다.

`/rocky:review-request` 2.5단계가 위험한 변경일 때 이걸 부른다. 그 밖에서도 부른다: 작업 중간에 방향을 점검할 때,
리뷰를 반영하다 원래 요구에서 벗어났는지 볼 때, 다른 호스트(Antigravity 등)에 넘긴 할 일이 돌아왔을 때.

## 1. 요구사항을 모은다 — 요약하지 않고 원문으로

리뷰어를 새 컨텍스트로 띄우는 건 구현한 쪽의 해석을 물려받지 않게 하려는 것이다. 이 세션이 요구사항을 고쳐 말하면
그 해석이 그대로 넘어간다. 그래서 **출처마다 원문을 인용하거나, 리뷰어가 직접 읽을 위치를 준다.**

아래를 모두 본다 — 앞의 것이 있어도 뒤의 것이 보완하는 경우가 많다.

1. **`$ARGUMENTS`** — 보드 참조(`rocky-12`)면 `todo_list { id }` 의 `description` 과 댓글, 이슈·PR 번호면
   `gh issue view` / `gh pr view` 의 본문, 경로면 그 파일, 그 밖의 문장이면 그 문장.
2. **이 대화의 사용자 발화** — 원 요청과, 그 뒤 범위를 줄이거나 넓힌 합의를 사용자가 쓴 그대로 인용한다. 에이전트가
   제안한 것은 사용자가 받아들인 것만 넣고 `제안 → 사용자 수락` 으로 표시한다.
3. **이 세션이 `start` 한 보드 할 일** — `description` 과 댓글(오너가 답을 다는 자리).
4. **스펙·계획 문서** — 위 출처가 가리키거나 이 브랜치가 건드린 `docs/design/specs/` · `docs/design/plans/` 문서.
   경로만 넘기고 리뷰어가 읽게 한다.
5. **이슈·PR 본문** — 이 브랜치에 열린 PR 이 있으면 그 본문과, 본문이 잇는 이슈.

출처끼리 어긋나면 **나중에 정한 것이 이긴다**(대화에서 합의한 변경 > 그보다 오래된 문서). 어긋났다는 사실도
리뷰어에게 그대로 알린다.

**하나도 못 찾으면 띄우지 않고 사용자에게 묻는다.** 요구사항 없이 보면 스타일 지적만 나온다.

## 2. 범위를 정한다

```bash
DEFAULT=$(git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null || echo origin/main)
BASE=$(git merge-base HEAD "$DEFAULT")
git diff --stat "$BASE"     # 커밋된 것 + 커밋 안 된 변경
git status --short          # ?? 로 보이는 새 파일은 diff 에 안 잡힌다 — 따로 알린다
```

인자가 PR 번호면 범위는 그 PR 이다(`gh pr diff <번호>`).

## 3. reviewer 를 띄운다

`reviewer` 서브에이전트를 띄우고, 세션 대화는 넘기지 않는다. 넘기는 것은 넷이다.

- **요구사항** — 1단계의 출처별 원문(또는 경로)을 출처 표시와 함께.
- **범위** — base SHA · HEAD SHA, 커밋 안 된 변경과 새 파일이 있는지.
- **무엇을 만들었나** — 사실만 한두 문장. 왜 그렇게 했는지는 넣지 않는다 — 리뷰어가 물려받으면 안 되는 게 그것이다.
- **볼 것과 출력** — 아래를 그대로 붙인다.

````markdown
요구사항 충족만 본다(검토 순서 1단계). 정확성·품질(2단계)은 보지 않는다 — `/code-review` 가 따로 본다.
요구사항을 항목으로 나눠 하나씩 판정하고, 아래 형식으로 답한다.

## 요구사항별 판정
| # | 요구사항(출처) | 판정 | 근거 |
| --- | --- | --- | --- |
| 1 | … | ✅ 충족 / ❌ 빠짐 / ⚠️ 다르게 해석 | `path:line` — ⚠️ 면 요구는 무엇이고 구현은 무엇인지 |

## ➕ 요청하지 않은 것
- `path:line` — 무엇인지 / 어느 요구에도 없다는 근거 (없으면 "없음")

## 판정
요구대로 됨 / 고친 뒤 됨 / 판단 보류 — 한두 문장. 보류면 사람이 무엇을 정해야 하는지.
````

## 4. 결과를 보고한다

- **결과는 채팅으로만 보고한다.** 보드 댓글·PR 코멘트로 남기지 않는다 — 사람이 원하면 그때 남긴다.
- ❌·⚠️ 가 리뷰어의 오독이면 코드나 테스트로 반증하고, 반증했다는 것도 함께 보고한다 — 새 컨텍스트는 사정을 모르기도 한다.
- 진짜 빠졌거나 어긋난 것은 고칠지 사람에게 묻는다. ⚠️ 는 특히 그렇다 — 어느 해석이 맞는지는 요구한 사람이 정한다.
- ➕ 는 빼거나, PR 본문에 요청 밖 변경이라고 밝힌다. 어느 쪽인지도 사람에게 묻는다.
