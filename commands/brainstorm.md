# brainstorm — 아이디어 → 설계

`$ARGUMENTS` 를 구현 가능한 설계로 다듬는다.

**이건 게이트가 아니라 도구다.** 사용자가 불렀을 때만 돈다. 작은 수정·버그 픽스·탐색적 작업에
이 절차를 강요하지 않는다. 반대로 되돌리기 어려운 선택(스키마, 공개 인터페이스, 의존성 추가,
프로세스 모델)이 걸린 작업이면 짧게라도 거치는 게 이득이다.

## 절차

### 1. 맥락부터 읽는다

질문하기 전에 현재 상태를 본다 — 관련 파일, `AGENTS.md`/`CLAUDE.md`, 최근 커밋, 기존 패턴.
**이미 코드에 답이 있는 걸 사용자에게 묻지 않는다.**

레포에 워크로그가 있으면 `worklog_search` 로 같은 주제의 과거 결정을 먼저 찾아본다 — 이미 내린
결정을 다시 논의하는 게 제일 큰 낭비다.

### 2. 스코프를 먼저 판정한다

요청이 독립적인 하위 시스템 여러 개를 담고 있으면(예: "채팅 + 파일저장 + 결제 + 분석 플랫폼")
세부를 파고들기 전에 그 사실부터 알린다. 쪼갤 단위와 순서를 제안하고, 첫 조각만 설계한다.

### 3. 한 번에 하나씩 묻는다

- 한 메시지에 질문 하나. 여러 개를 몰아 던지지 않는다.
- 가능하면 선택지를 제시한다(`AskUserQuestion`). 열린 질문도 필요하면 쓴다.
- 초점은 셋: **목적 / 제약 / 성공 기준**.
- 답이 달라도 결과가 같은 질문은 하지 않는다. 그냥 정하고 넘어간다.

### 4. 접근안 2~3개를 트레이드오프와 함께

추천안을 **먼저** 놓고 이유를 말한다. 나머지는 왜 아닌지 한 줄씩. 선택지 나열만 하고 판단을
미루지 않는다.

### 5. 설계를 제시한다

- 각 절의 길이를 복잡도에 맞춘다 — 뻔하면 두세 문장, 미묘하면 문단 하나.
- 다룰 것: 구조, 경계(어디까지가 이 단위의 책임인가), 데이터 흐름, 실패 처리, 검증 방법.
- 단위를 나눌 땐 기준 하나로 판정한다 — **내부를 읽지 않고도 무엇을 하는지 알 수 있는가.**
  아니면 경계가 잘못된 것이다.
- 기존 코드베이스라면 기존 패턴을 따른다. 이번 목표에 걸리는 문제는 설계에 포함해 고치고,
  **무관한 리팩터는 제안하지 않는다.**

### 6. 스펙 문서 — 필요할 때만

설계가 크거나(여러 세션에 걸침, 다른 에이전트에게 넘김, 나중에 되돌아볼 것) 사용자가 요청하면
`docs/design/specs/YYYY-MM-DD-<topic>-design.md` 로 저장한다. 작은 설계는 대화에 남기고 끝낸다.

저장했다면 쓰고 나서 한 번 훑는다: 남은 `TBD`/`TODO`, 서로 모순되는 절, 두 가지로 읽히는 요구사항.
발견하면 그 자리에서 고치고 넘어간다 — 재검토 루프는 돌지 않는다.

## 시각 자료가 필요할 때

레이아웃·다이어그램·비교처럼 **말보다 보여주는 게 나은** 질문이 나오면 아티팩트로 만든다.
localhost 브라우저 컴패니언은 제안하지 않는다 — 모바일에서 열리지 않는다.

UI 를 *주제로* 다루는 질문과 *시각적인* 질문은 다르다. "이 화면의 성격이 뭐야"는 텍스트 질문,
"두 레이아웃 중 뭐가 나아"는 시각 질문이다.

## 원칙

- **YAGNI.** 설계에서 지금 필요 없는 걸 걷어낸다.
- **되돌아갈 수 있다.** 중간에 말이 안 맞으면 앞으로 돌아가 다시 묻는다.
- **끝나면 구현으로.** 설계 승인 후 계획 문서가 필요할 만큼 크면 `docs/design/plans/` 에 남기고,
  아니면 바로 구현한다. 판단은 규모로 한다.
